### Autopilot-stack

Build a sequence of dependent changes and deliver a reviewable stack within the user's publication boundary. The operator landing the stack does not remove engineering acceptance requirements.

1. Follow Autopilot-full for native queue, briefs, delegated ownership and decisions. Store no parallel children or decision TSV.
2. Record parent bases, actual head versions, dependency contracts and shared writer ownership in existing Plans. One writer integrates a branch. Read the current checkout methods; do not load an assumed origin/main:pstack path.
3. Verify each independently acceptable outcome through its Plan checks. Review accepted changes before appending a child. Record conflicts and upstream handoff; do not use patch-id as native evidence reuse.
4. Prepare a linear stack using available Git/forge tools when requested. Keep merge authorization separate from CI and method verdicts. No mandatory Graphite, cloud runtime or fixed live-worker count.
5. On requested scheduled audits use the host automation tool with meaningful-change notifications. Otherwise complete current work in-session.
6. Deliver actual PR/branch links and head versions, Plan/Release evidence, the safe landing order, and unresolved conditions. Do not land a stack the user reserved for their own review.
