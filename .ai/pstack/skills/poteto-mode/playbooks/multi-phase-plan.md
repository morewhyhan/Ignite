### Multi-phase or multi-PR plan

You own a plan another agent can execute and a reader can audit. Planning alone does not authorize implementation or external publishing.

1. Read the relevant Feature and native Plan rules. Continue the unfinished Plan covering the outcome. Use the native change/module scaffold only for a new independently acceptable outcome. Small work uses the exemptions in docs/plans/README.md, not an arbitrary file count.
2. Resolve observable questions from existing evidence or a bounded prototype. Record genuine product decisions and remaining questions in the Plan. Prototype observations do not replace actual acceptance checks.
3. Partition investigation only when useful. Give each delegate goal, paths, current REQ/AC, constraints, evidence and a stop condition. Use models and tools available in this host.
4. Fill docs/plans/_template.md structured metadata. One independently acceptable result is one Plan; API, UI, tests and final status updates are tasks of that Plan. Native tasks are the sole task status. Do not copy a second checkbox program skeleton.
5. Map every original goal and constraint to Feature REQ/AC, tasks, write_scope and evidence. Put dependency contracts, shared files and handoff in the existing fields. A multi-Plan result uses a Release scope with complete AC coverage.
6. Select required unit/database/browser/external layers from actual behavior and risk. Real data and pages require real behavior checks. Performance measurement is required for a performance outcome, not for every method/document change. Use existing harnesses; there is no mandatory ten-worker swarm or new control plugin.
7. Validate through the native Plan commands. Before ready, settle actual open questions and review semantic coverage. During authorized execution use pnpm ignite tdd red --plan <ID> --ac <AC>, then pnpm ignite check --plan <ID> --level auto. Reuse valid same-input runs. The inherited check-plan.mjs skeleton checker is not the Ignite validator.
8. Report the Plan path, dependencies, choices and unresolved gates. A planning-only request stops at this deliverable; an existing execution authorization proceeds without another start approval.

Record alternative designs and prototype links in the Plan. Long-lived architectural decisions may need an ADR; observed system facts belong in Design. A scheduled audit uses the host automation facility only when requested, with unchanged-state silence. Read the current checked-out .ai/pstack method files unless the user explicitly requests a remote version.
