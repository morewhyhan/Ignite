
### Refactoring

**You own the contract. The structure changes. The behavior does not.** Distinct from Feature, which adds behavior, and Bug fix, which corrects it.

Keep a discovered defect in the current Plan when it prevents this outcome or violates its required safety boundary. Only an independently acceptable follow-up gets a separate Plan within authorized scope. A change to intended behavior routes to Feature or Bug fix while preserving the original outcome's ownership. Large or cross-cutting structural work uses **figure-it-out**.

1. Pin the behavior contract first. Run the **how** skill over the affected subsystem to learn the contract, then write a characterization test, snapshot, or equivalence harness that captures current behavior before any structure moves. If the area has no coverage, write the pin before touching structure. Type check and lint are not a pin.
   A green characterization pin does not replace a new Plan's required behavioral red. An improved observable contract needs its actual failing assertion before implementation, under [testing rules](../../../../../docs/standards/testing.md#测试先行). Do not break correct behavior, use an environment error, or add a placeholder failure to manufacture red. If the required evidence is missing, retain the gap in the original Plan; this playbook grants no exemption.
2. Name the structure the code is missing per **principle-model-the-domain**. Boring code stays when the shape is already clear and local. The reshape must delete branches or invalid states, not add indirection.
3. Name the target shape. State what the module layout, types, and call graph should be if built today (**principle-foundational-thinking**, **principle-redesign-from-first-principles**). Use **architect** for a consequential boundary or competing viable shapes. Parallel exploration needs useful independent scopes; crossing a function boundary alone does not require it.
4. Subtract before you add. Delete dead code, collapse one-caller wrappers, drop redundant validators, and remove orphan references before introducing the new shape (**principle-subtract-before-you-add**). The smallest change that reaches the target shape ships (**principle-laziness-protocol**). A speculative cleanup that "might help" gets reverted.
5. Move in small behavior-preserving steps, each keeping the pin green. For eligible internal API reshapes, migrate every caller and delete the old API in the same wave (**principle-migrate-callers-then-delete-legacy-apis**). Preserve applied database migrations. Spot-check renames in code, strings, prose, and back-references. Delegate mechanical edits only when they form a useful independent scope with exclusive paths and a stated behavior contract; otherwise execute directly. Configured role "feature, refactoring" inherits the host when unspecified.
6. Prove behavior is unchanged on the real artifact, not "it compiles" (**principle-prove-it-works**). For larger reshapes, run an equivalence check: a script that diffs old-vs-new outputs, a recorded baseline replayed against the new code, or a smoke run on the matching surface via the relevant control skill.
7. Confirm the change is worth keeping. The success measure is reduced reader load (**principle-minimize-reader-load**). If the diff does not lower reader load somewhere, revert it.
8. Order reviewable units as subtraction, reshape, and necessary cleanup. Use **sequence-verifiable-units** and reuse valid matching checks. Rebase only when the actual integration needs it and authorization covers the branch; preserve other contributors' work. Use **Opening a PR** when the authorized delivery needs one; otherwise deliver the local diff with native evidence.

**Reply:** the structure that changed, the pinned contract, equivalence evidence, reader-load change, and what was retained or reverted. If a necessary defect was corrected in the same outcome, state that behavior change and its separate proof.
