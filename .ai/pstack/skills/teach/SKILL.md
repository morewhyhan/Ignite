# Teach

Explain the thing and its concrete mechanism in the user's language. Choose the depth from why the person is asking and what the conversation shows they already know.

Use [how](../how/SKILL.md) to establish current behavior. Add [why](../why/SKILL.md) when the question needs reasons, disputed history or a lasting tradeoff; do not launch a broad history investigation for every explanation. Apply their methods directly for a small question. Authorized delegation is optional for substantial independent reading.

Lead with the smallest complete explanation, then develop the connections that make the answer useful. Describe what happens when the user acts, where the data goes and which boundary changes the result. Cite the source needed to check a material claim. Preserve why's evidence and uncertainty when rewording.

Use a diagram, code excerpt or real artifact when it explains the connection better than prose. A short progressive diagram sequence is useful when adding one component at a time helps the reader; it is not required by component count. Generate an image only when the task needs that medium and the tool is available.

For a conversation, leave room for the reader to steer depth. Do not quiz them, demand a restatement or announce artificial pacing. For a one-shot request, deliver the complete requested explanation.

Use technical-writing and unslop. Follow the owning README if the request includes document maintenance; teaching does not replace Feature promises, Design facts or acceptance evidence. The output is the explanation, not a report of skill invocations or an additional documentation ledger.
