# 术语与状态词对照

本文件统一仓库内三组容易混用的说法，以及 Plan、证据、Release 三套状态词的对应关系。
新增文档时优先使用本表的词；历史文档保留原措辞，不做批量改写。

## 一、术语对照

| 仓库里的旧说法     | 现在统一叫        | 含义                                                      | 出现在哪里                            |
| ------------------ | ----------------- | --------------------------------------------------------- | ------------------------------------- |
| 原始目标、用户诉求 | goal              | 用户实际要的结果，写在 Plan 元数据 goals 与 Release scope | Plan 元数据、Release scope            |
| 矛盾、主要矛盾     | 整体判断          | 对"为什么现在要做、先做什么"的判断，不只是罗列问题        | Plan「主要矛盾」章节                  |
| 绑定、绑定记录     | evidence binding  | 把 REQ / AC / 测试 / 运行记录串起来的那组字段             | Plan 元数据 acceptance、Release scope |
| 红灯               | red evidence      | 实现之前记录的目标行为失败                                | docs/others/evidence/tdd/             |
| 回写               | design write-back | 计划完成后更新设计文档并登记                              | docs/others/design-writeback.md       |

## 二、三套状态词

### Plan 状态

| 状态       | 含义                                 | 能否改实现 |
| ---------- | ------------------------------------ | ---------- |
| draft      | 规格已写，未过审查                   | 可以       |
| ready      | 通过草稿审查，等开工                 | 可以       |
| active     | 已取红灯或正在实现                   | 可以       |
| verifying  | 实现完成，等集成证据                 | 不再改     |
| done       | 集成检查、交付检查、发布验收全部通过 | 不再改     |
| blocked    | 外部条件不满足                       | 不改       |
| cancelled  | 主动放弃，保留记录                   | 不改       |
| superseded | 被新计划取代                         | 不改       |

### 证据状态

| 状态      | 含义                                   |
| --------- | -------------------------------------- |
| red       | 目标行为断言失败，且测试文件此后未改动 |
| green     | 实现后同一测试通过                     |
| stale     | 证据对应的提交或测试已变化，不能再用   |
| restarted | 明确记录重启原因，旧红灯作废           |

### Release 状态

| 状态     | 含义                         | 与 Plan 的关系      |
| -------- | ---------------------------- | ------------------- |
| included | 该目标由已列入的 Plan 交付   | 对应 Plan 必须 done |
| deferred | 本轮不做，写明原因或触发条件 | 可以没有 Plan       |
| excluded | 明确不做，写明理由           | 可以没有 Plan       |

三套状态不能互相冒充：Plan done 不等于 Release 验收通过；Release included 也不代表对应 Plan 已完成。

## 三、两条历史延期项的处置

### 1. 文档定稿状态机

处置：**不单独实现，记为非目标。**

理由：文档"是否定稿"已由两处承担——Plan 状态（draft → ready → done）与设计文档的状态标记（当前事实 / 目标设计）。
再引入第三套文档状态会与这两处冲突，收益不足以抵消理解成本。

### 2. 领域事件与命令记录

处置：**继续延期，写明触发条件。**

触发条件：出现跨聚合的业务流程（一次操作要改两个以上聚合，且需要补偿或重放）。
当前模板只有一个 HTTP 入口与单一任务聚合，用事务即可，不需要事件流。
触发后应新建独立 Plan，引入事件记录表与命令日志，不在本闭环内顺带实现。
