# GOAL 规格

> 文档状态：定稿
>
> **给人和辅助写作的 AI 用。** 本文规定 GOAL 写什么、按什么顺序想清楚、每层必须写清什么。
> 维护流程（每轮怎么读、怎么回写、怎么检查）见 [目标树标准](../../standards/goal-tree.md)。

## 一、GOAL 是干什么用的

它是三样东西：

```
1. 需求真源      要什么、做到没有
2. 架构设计载体  领域怎么切、规则挂在哪、为什么这样切
3. 人机接口      人只改这里；Agent 从这里取需求，把结论写回这里
```

它不写：系统现在长什么样（那是 `docs/designs/`）、工程规则（那是 `docs/standards/`）、逐条测试代码（那是 `tests/` 与 `docs/others/test-cases/`）。

写这份文档的过程，就是一次建模。建模的意思是：先把现实里的业务看清楚，找出里面固定不变的东西，再把它搬到代码里；不是先画数据库表，再往表上套界面。

## 二、谁在什么时候用它

| 角色 | 什么时候 | 做什么 |
| --- | --- | --- |
| 人 | 立项、改需求 | 写目标、领域、规则、验收；改完跑 `pnpm goal:audit --record` |
| Agent | 每轮开工前 | 从目标读到用例，找到本轮 REQ 与 AC |
| Agent | 每轮收尾 | 跑测试，把状态与证据写回用例行 |
| 脚本 | 每次状态变化 | 更新汇总与状态，不写内容 |

## 三、五个层级

```
第 1 级  目标        这套软件最终让人完成什么
第 2 级  领域        一块业务边界：一套词、一套规则、一个边界
第 3 级  REQ         这个边界里必须成立的规则
第 4 级  AC          用户做什么、看到什么
第 5 级  测试用例    怎么证明这条 AC 成立
```

### 每级必须写清什么

| 层级 | 必填 | 说明 |
| --- | --- | --- |
| 目标 | 一句话 | 可判定：做到没有能回答 |
| 领域 | 事件链、聚合、边界、为什么这样切、术语 | 见下 |
| REQ | 来源事件、规则 | 规则要能判定真假 |
| AC | Given / When / Then | 用户能观察到的结果 |
| 测试用例 | 怎么测、结果、证据 | 结果写通过或失败 |

领域五个字段的意思：

```
事件链       这个领域里用户做了什么、系统发生了什么
聚合         哪些东西必须一起变化、一起保证一致
边界         管什么、不管什么
为什么这样切  合并或切开的依据
术语         本领域里每个词只有一个含义
```

## 四、十个步骤

十个步骤，分四段：想清楚（1–6）、写成规则（7–8）、挂证据（9）、回审（10）。每一步写清：回答什么、输入、产出、约束、完成标准。

| 步 | 名称 | 产出写在哪 | 完成标志 |
| --- | --- | --- | --- |
| 1 | 写目标 | GOAL 第 1 级 | 能回答做到没有 |
| 2 | 事件风暴 | 事件清单 | 覆盖全部用户旅程 |
| 3 | 命令风暴 | 命令清单 | 每个事件都有发起者与输入 |
| 4 | 识别模型 | 实体、值对象、聚合、聚合根 | 每个名词都有归属 |
| 5 | 识别上下文 | 领域 | 边界互斥、事件都有归属 |
| 6 | 通用语言 | 术语表 | 一词一义 |
| 7 | 写 REQ | GOAL 第 3 级 | 每条能判定真假 |
| 8 | 写 AC | GOAL 第 4 级 | 用户能观察到 |
| 9 | 挂用例 | GOAL 第 5 级 | 有结果与证据 |
| 10 | 回审 | 修订记录 | 两项检查全过 |

### 第 1 步 写目标

- 回答：这套软件最终让人完成什么。
- 输入：用户的原始诉求，尽量保留原话。
- 产出：GOAL 第 1 级，一句话。
- 约束：
  - 不写技术方案。先把业务逻辑建模，再完成技术实现；技术细节无非是响应用户操作和持久化模型。
  - 不写“支持、优化、完善”这类无法判定的词。
  - 一句话内说完，不举例子、不列功能。
- 完成标准：换一个人读，能回答“做到没有”。

### 第 2 步 事件风暴

- 回答：用户做了什么、系统发生了什么。
- 输入：目标、用户旅程、现有页面或流程。
- 产出：事件清单，一行一个，用过去式（注册成功、任务创建、登出完成）。
- 约束：
  - 先不分类、不评价、不合并。做法是把事件写在纸条上贴到墙上，通过事件追溯关键行为，确定系统状态的变化。
  - 只写会对系统状态造成改变的事。原文的说法是：事件捕获我们在建模的领域里发生过、并且会对系统产生影响的事情。
  - 表达方式写“某个状态被改变”，例如“订单已创建”，不写“用户点击了按钮”。
  - 一个事件只描述一件事，不把“注册并登录”写成一条。
  - 想不清楚时，把“电”断掉，假装自己是服务员，用纸和笔把流程走一遍。
  - 一个事件要写全结果：成功、失败、被拒各是一条链，不能只写成功那条。
  - 每条链写清两样：必要条件（缺一不可）和充分路径（能走通的一条路）。
  - 路径要有起点和终点：用户从哪个页面来、最后停在哪。
  - 例子：提交注册 → 注册成功（账号创建、会话建立、进工作台）；提交注册 → 注册失败（邮箱已占用或密码不合规、提示、留在注册页）。
  - 写路径时记住：上一层的目标，下一层就是它的必要条件；同一层里有多条充分路径，路径要在树上分叉，不能并成一条直线。
- 完成标准：每条用户旅程都能在清单里从头走到尾。

### 第 3 步 命令风暴

- 回答：每个事件由谁发起、要什么输入、要什么权限。
- 输入：事件清单。
- 产出：命令清单，一行一个命令，标注发起者、输入、权限。
- 约束：
  - 命令是产生事件的行为，例如用户提交表单、第三方回调、定时任务。一个命令触发一个事件。
  - 命令有三类来源：用户的动作、第三方系统、定时器。三类都要写，不要只写用户点击。
  - 分析命令的目的，是把事件的触发源找出来，从而找出系统里的角色，包括外部系统和定时器这些隐含角色。
  - 权限要写“谁不能做”，不写“支持权限控制”。
  - 命令对应接口，事件对应状态变化；两者不要混在一张清单里。
- 完成标准：每个事件都能找到发起它的命令；每个命令都能说出被拒绝的条件。

### 第 4 步 识别模型

- 回答：哪些名词承载状态与规则。
- 输入：事件与命令清单。
- 产出：实体、值对象、聚合、聚合根。
- 约束：
  - 有身份、会变的才叫实体；只由属性决定的是值对象。原文的例子：银行账户有 ID，币种和余额变了还是同一个账户；交易单里的金额由币种和数值组成，改任何一个，金额就不再是原来那个。
  - 一组必须一起变化、一起保证一致的东西放进聚合，聚合有且只有一个聚合根；要管理聚合必须通过聚合根，外部不能直接改聚合内部的实体。
  - 聚合最多两三层。原文的说法是：层级过深会带来落地上的巨大成本，两三层已经能满足大部分场景，超过三层就考虑拆。
  - 分清“关联”和“拥有”：生命周期一致才放进聚合。原文的例子：开户申请和账户之间是关联，不是拥有；把申请塞进账户聚合，聚合会变得很大，生命周期也不一致。
  - 多对多关系要问中间模型归谁。原文的例子：用户和空间是多对多，中间那个“成员”不是一张没含义的中间表，它有加入时间、状态，应该归属到空间。
- 完成标准：事件里出现的每个名词都有归属；每个聚合能一句话说清它保证什么一致。

### 第 5 步 识别上下文

- 回答：这些模型该怎么切成领域。
- 输入：模型清单与事件链。
- 产出：领域清单，每个领域一段。
- 约束：
  - 同一个词在两处含义不同就切开。原文的例子：商品在物流、交易、支付里含义完全不一样，它们处在不同上下文。
  - 同一条事件链就合并；一个领域只回答一类问题。
  - 领域是问题，上下文是解。原文的说法是：领域是业务问题，设计出来的模型是解的一部分；领域导出上下文，上下文支撑领域，不是包含关系。
  - 领域按重要性分三类：核心域（业务成功的主要促成因素，一般一个系统只有一个）、支撑域（完成业务必需，但不是成功原因，比如登录、找回密码）、通用域（被整个系统使用，可以买现成的，比如文件服务、通知服务）。
  - 切完要能写出“管什么、不管什么”，并且任意两个领域的边界不重叠。
- 完成标准：每个事件恰好属于一个领域；任意两个领域的边界不重叠。

### 第 6 步 通用语言

- 回答：每个领域里的词到底是什么意思。
- 输入：领域清单。
- 产出：术语表，一行一个词。
- 约束：
  - 一个词只在一个领域里有一个含义；同义词只留一个。原文的例子：报销系统里 bill 指消费账单，ticket 指提交的工单，都译成“单据”就会打架。
  - 通用语言是业务人员和开发人员使用无歧义的统一语言来对话，包括对概念的统一理解和定义。
  - 不用“等等、相关、其他”这类模糊词。
  - 词要写进 GOAL 的领域节点，不另建词表。
- 完成标准：把术语表给一个新读者，他能用这些词复述领域规则而不产生歧义。

### 第 7 步 写 REQ

- 回答：这个领域里哪条规则必须成立。
- 输入：事件、命令、聚合。
- 产出：GOAL 第 3 级，每条 REQ 带来源事件。
- 约束：
  - 一条 REQ 只写一条规则；能判定真假。
  - 不写实现方式：不写接口、字段、状态码。
  - 必须能指回至少一个事件；指不回去的规则，要么事件漏了，要么规则是臆想的。
  - 规则要能说清“违反它会怎样”，说不清就是空话。
- 完成标准：每条 REQ 都能举出一个违反它的真实场景。

### 第 8 步 写 AC

- 回答：用户做什么、看到什么，才算这条规则成立。
- 输入：REQ。
- 产出：GOAL 第 4 级，Given / When / Then。
- 约束：
  - 只写用户能观察到的结果；不写状态码、字段名、内部调用。
  - 至少覆盖一条异常或边界：没登录、没权限、输入非法、资源不存在。
  - 一条 REQ 可以有多条 AC；一条 AC 只证明一条 REQ。
  - AC 之间不重复；重复的 AC 合并。
- 完成标准：把 AC 交给测试人员，他能写出测试而不用再问。

### 第 9 步 挂用例

- 回答：怎么证明这条 AC 成立。
- 输入：AC。
- 产出：GOAL 第 5 级，一条用例一行，带结果与证据。
- 约束：
  - 一条 AC 至少一条用例；浏览器类必须截图。
  - 结果只能写通过或失败，不写“基本可用”。
  - 证据要能打开：运行日志或截图。
  - 用例要写清“怎么测”，不是只写“测过了”。
- 完成标准：点开用例行，能看到测了什么、结果、证据在哪。

### 第 10 步 回审

- 回答：前面九步有没有漏、有没有打架。
- 输入：整份 GOAL。
- 产出：修订后的 GOAL 与审计记录。
- 约束：
  - 事件必须都有归属；领域边界必须互斥；每个词只能一个含义。
  - 改完必须重跑审计并记录，记录绑当前 GOAL。
- 完成标准：`pnpm goal:audit` 与 `pnpm goal:trace` 都通过。

前六步是想，后四步是写。**写 GOAL 的过程就是建模的过程。**

## 五、这些词到底是什么意思

这一节不是词典，是把原文里讲这些词的地方整段搬过来，再说明它在写 GOAL 时怎么用。
原文段落直接放在引用块里，不做删改；引用块后面是解释。

### 领域

> 领域是软件要解决的业务问题和诉求。通俗来说，领域就是业务需求。不过这些业务有一些内在逻辑需要分析，存在一些专业性，比如财务、CRM、OA、电商等不同领域。计算机只是自动化的处理领域问题，领域知识可能不是开发人员擅长的。

> 领域（Domain）是业务相关知识的集合。构成领域的要素就是特定的业务场景。

两段话合起来看：领域不是“用户管理模块”，也不是“订单表”，而是**一类业务问题的总和**，由一个个具体场景组成。签合同、买保险、注册账号、建一条任务，都是场景；把同类场景归在一起，才是领域。

原文还有一段更直白的例子，讲的是为什么不能上来就写代码：

> 我们往往马上关注到数据库的设计上，想当然的设计出一些数据库表，然后着手于界面、网络请求、如何操作数据库上，业务逻辑被封装到一个叫做 Service 对象上，这个对象不承载任何状态，业务逻辑通过修改数据库实现。

> 麻烦在于，当业务复杂后，这种模式会带来一些问题。虽然最终都是对数据库的修改，但是中间存在大量的业务逻辑，并没有得到良好的封装。客人退菜，并不是将订单中的菜品移除这么简单。需要将订单的总额重新计算，以及需要通知后厨尝试撤回在做的菜。不长眼的新手程序员擅自修改数据片段，整体业务逻辑被破坏。

这段说明：领域的边界，往往就藏在“一个动作背后要连带改哪些东西”里。退菜不是一个删除，它牵动总额、后厨、订单状态；这些必须一起变的东西，就是一个聚合的雏形。

在 GOAL 里怎么用：

```
1. 先列场景，不要先列功能
2. 同类场景归成一个领域
3. 每个领域一句话说清“管什么、不管什么”
4. 说不清边界的，说明还没想清楚，不要急着往下写
```

反例：把“认证”和“权限”合成一个领域。它们的场景不同（登录 vs 谁能看什么），词义也不同，合在一起会让规则互相污染。

### 子域

> 核心子域指业务成功的主要促成因素，是企业的核心竞争力。一般一个系统只存在一个核心子域，并应该投入最好的资源到这个领域。

> 支撑子域不是核心，不被整个系统使用，完成业务的必要能力，但不是业务成功的原因。例如电商系统中，会员系统必不可少但是应该作为支撑订单等业务来考虑。

> 通用子域不是核心，但被整个业务系统所使用，通用子域可以看做特殊的支撑子域。通用子域可以使用业界主流通用方案，例如文件服务、通知服务、推送、舆情等。甚至可以考虑购买更专业企业提供的服务。

这三段的区别不在技术，而在**投入策略**：

| 类型 | 判断标准 | 资源策略 | 在 GOAL 里怎么体现 |
| --- | --- | --- | --- |
| 核心子域 | 业务成功靠它 | 最好的人、最多的验证 | 规则写得最细，AC 覆盖最全 |
| 支撑子域 | 必须有，但不是差异 | 够用就行，别过度设计 | 规则写清，够验收即可 |
| 通用子域 | 全系统都用，可替代 | 优先用现成方案 | 尽量少写自研规则 |

例子：一个任务管理产品，任务本身是核心子域，认证是支撑子域，邮件通知是通用子域。反过来，如果产品卖点是“企业级单点登录”，认证就可能是核心子域。**同一个能力，在不同产品里类型不同。**

在 GOAL 里怎么用：每个领域节点写一行类型。类型不写进代码，只决定你在这里花多少力气。

### 领域模型

> 领域模型是业务概念在程序中的一种表达方式。面向对象的编程语言使用类作为业务概念的承载体，也可以用 UML 可视化的表达模型。模型是用来设计和理解整个软件结构，切记不要事无巨细的模型。在模型思维中，模型是简单的，能反应业务概念即可。

> 模型，用来反映事物某部分特征的物件。要想做好一个可持续维护的 IT 系统，实际上需要对业务进行充分的抽象，找出这些隐藏的模型，并搬到系统中来。如果发生在餐厅的所有事物，都要能在系统中找到对应的对象，那么这个系统的业务逻辑就非常完备。

原文对“怎么找模型”给了一个很土但有效的办法：

> 后来，如果我什么业务逻辑想不清楚，我就会把电断掉，假装自己是服务员，用纸和笔走一遍业务流程。

这句话的意思是：不要一上来想表和接口，先想“现实里这件事是怎么完成的，谁在什么情况下做了什么，产生了什么结果”。纸笔能走通的流程，代码才可能写对。

在 GOAL 里怎么用：领域节点下的“事件链”和“聚合”就是模型的骨架；写不出来，说明还没想清楚，不要用“等等、其他”糊过去。

### 通用语言

> 通用语言是指在软件设计中，业务人员和开发人员需要使用无歧义的统一语言来对话。这些语言包括对概念的统一理解和定义，以及业务人员参与到软件建模中，否则业务的变化会造成软件巨大的变化。

> 在不同的上下文中不同的名词代表的含义不一样，例如一个报销系统中 bill、ticket 都有单据的含义，但是 bill 可能指消费的账单，ticket 指在系统中提交的包含 bill 的工单。同样也需要统一技术语言和业务语言。领域专家眼里的“流程图”和工程师眼中的“流程图”有时候非常不一样。

这里的重点不是“大家用一个词”，而是**同一个词在同一上下文里只有一个含义**。跨上下文时，同一个词可以不同义，但必须各说各的，不能共用。

为什么重要：需求文档里一旦出现一词多义，后面每条 REQ 都可能被两种理解解释，测试也无法判定对错。

在 GOAL 里怎么用：

```
1. 每个领域节点写一行“术语：”，列本领域的词和定义
2. 同一个词在两个领域含义不同，必须分开写，不能只写一次
3. 定义要能造句子，例如“会话 = 一次登录的凭证”
4. 发现两个词其实是一个意思，合并；发现一个词是两个意思，拆开
```

反例：认证领域里“用户”指有账号的人，任务领域里“用户”指任务的所有者；如果两处都只写“用户”，规则会互相污染。正确做法是任务领域写“所有者”，并注明“所有者 = 任务所属的账号”。

### 实体

> 实体是领域模型面向对象语言的具体体现，一般是一个类。实体可以使用 ID 标识。

> 实体可以使用 ID 标识，但是值对象是用属性标识，任何属性的变化都视为新的对象。比如一个银行账户，可以由 ID 唯一标识，币种和余额可以被修改但是还是同一个账户。

拆开看，实体有三个特征：

```
1. 有身份：哪怕属性全变了，还是同一个东西
2. 有生命周期：会创建、会修改、会删除
3. 需要被追踪：外部要靠 ID 找到它
```

例子：用户（改了昵称还是同一个人）、任务（改了标题还是同一条任务）、订单（改了地址还是同一张订单）。

反例：把“邮箱”做成实体。邮箱改了就是另一个邮箱，它没有独立生命周期，应该是用户的属性或值对象。

在 GOAL 里怎么用：事件里出现的名词，先问“它有没有 ID、会不会被单独追踪”；答是，才是实体，才可能进聚合。

### 值对象

> 值对象是一种特殊的实体，但一般认为没有自己的状态和生命周期。值对象是用属性标识，任何属性的变化都视为新的对象。交易单中的金额由币种和数值组成，无论修改哪一个属性，金额都不再是原来的金额。

这段话里最关键的是最后一句：值对象**没有“改”这个概念**，只有“换成一个新的”。100 元改成 120 元，不是同一个金额变了，而是换了一个金额。

判别方法：

```
问：它需不需要独立追踪？不需要 → 值对象
问：它改一个属性，还是原来的东西吗？不是 → 值对象
问：它有没有自己的生命周期？没有 → 值对象
```

例子：金额、邮箱、地址、时间段、坐标。

在 GOAL 里怎么用：聚合内部尽量用值对象，减少实体数量；值对象不要给 ID，也不要有自己的表。

反例：把“地址”做成一张表、一个 ID，然后让订单指向地址 ID。地址改了，历史订单的地址也跟着变——这就是原文说的“交易类数据要锁定当时快照”的反面。

### 聚合与聚合根

> 聚合是一组生命周期一致的实体集合，表达统一的业务意义。聚合的意义在于让业务统一、一致，在面向对象中有非常重要价值。

> 聚合根是聚合中最核心的对象，是聚合的领航员。要管理聚合必须使用一个聚合根，然后使用聚合根来实现发现、持久化聚合的作用。聚合中有且只有一个聚合根，一个实体可以独立作为一个聚合。

> 聚合是一组相关领域模型的集合，是用来封装业务的不变性。通过定义对象之间清晰的所属关系和边界，确保关系紧密的领域模型能够内聚在一起。

三句话的核心是“**不变性**”：聚合存在的目的，是保证某几条业务规则在任何时候都成立。比如订单总额必须等于订单项之和；这条规则成立的范围，就是聚合的边界。

原文还讲了持久化带来的现实问题：

> 聚合被赋予了两个责任：负责业务的一致性；负责数据的整体存储。第二点让聚合的持久化变得困难和性能低下。一个简单的道理是，我们只需要一个橘子，却总想把橘子树搬来搬去。

意思是：一致性边界和存储边界不完全是一回事。为了性能，有时会只加载聚合的一部分；但业务规则上，仍然要把它们当一个整体来校验。写 GOAL 时不必规定怎么存，但必须说清哪些东西必须一起变。

原文列了几条很具体的战术原则，直接可以当检查表：

> 1. 当一个实体被多个聚合根使用时，需要将其设计为聚合根或者将其拆开，不能再作为实体使用。

> 2. 不允许使用中间表处理多对多关系，探明多对多原因，明确中间模型的归属。

> 3. 区分关联和拥有，避免将本应该关联的模型设计到聚合之下，否则聚合非常大。

> 5. 聚合的层级保持在 2 级，最多不超过 3 级。

> 6. 事实数据快照化。

> 7. 核心交易，设计交易流水或日志，用于审计。

逐条解释：

```
第 1 条：一个实体被两个聚合共用，说明它其实是独立的聚合根，或者该拆开；共用实体会让两个聚合耦合
第 2 条：多对多不是加一张没含义的中间表，要问中间那个东西归谁；它往往有自己的时间、状态、生命周期
第 3 条：生命周期不一致的，用关联；放进聚合就会让聚合过大、更新困难
第 5 条：聚合两三层足够，再深就拆
第 6 条：合同、订单这类事实数据，要锁定当时的快照，不跟着源数据变
第 7 条：核心交易留流水，出问题能对账
```

原文还给了一个判断聚合是否过大的例子：

> 一个不佳的设计是，账户不能将开户申请纳入聚合中，因为申请的生命周期和账户并没有关系。开户申请和账户之间可以存在关联，但是不应该具有拥有关系。

在 GOAL 里怎么用：领域节点写“聚合：”，只写聚合根和它保证的那条一致性，不写表结构。例如“用户 + 会话”表示“会话必须属于一个存在的用户，删除用户时会话一起失效”。

### 限界上下文

> 限界上下文是有统一业务目标和概念的聚合组成的集合。大型项目都会存在多种模型，这些模型在不同的上下文中，可能有相似业务概念，但是他们的业务目标完全不一样。

> 识别上下文可以从概念的二义性着手，比如商品的概念在物流、交易、支付含义完全不一样，但具有不同内涵和外延，实际上他们处在不同上下文。界限上下文可以用于微服务划分、避免模型的不正确复用带来的问题。

> 如果领域的构成要件是场景，上下文的构成要件是模型，那么领域和上下文之间就没有包含和被包含关系。他们构成：上下文支撑领域的关系，领域导出上下文的关系。

这三段把两个容易混的概念分开了：

| | 领域 | 上下文 |
| --- | --- | --- |
| 本质 | 业务问题 | 解决这个问题的一组模型 |
| 构成 | 场景 | 模型与词 |
| 关系 | 问题 | 解 |

所以“一个领域对应一个上下文”不是硬规则；写 GOAL 时把领域当边界用，一个领域里尽量只放一套模型、一套词。

在 GOAL 里怎么用：领域的“为什么这样切”写的就是上下文边界——哪些模型必须共享一套词，哪些同名不同义必须分开。

### 事件

> 事件：捕获我们所建模的领域中所发生过的事情，会对系统产生影响的事情。

> 表达事件最好的方式是，描述系统的某个状态被改变。例如订单已创建。

> 事件的触发源有哪些？另外一个事件、系统中的命令。

要点：

```
1. 已经发生，用过去式：注册成功、任务创建、登出完成
2. 会对状态造成改变；不改变状态的（比如滚动屏幕）不是事件
3. 一个事件可以触发另一个事件；由事件触发的事件，不必贴触发源
4. 事件是业务事实，不写“调用接口”“写数据库”
```

一个辨析的例子：滚动屏幕算不算事件？取决于系统是否记录它。不记录，它就是系统之外的行为；如果要做行为分析、记录“用户行为已记录”，它才是事件。

在 GOAL 里怎么用：领域节点的“事件链”就是按时间顺序排好的事件；REQ 必须标“来源事件”，指不回去的规则多半是拍脑袋。

### 命令

> 命令：产生事件的某种行为，例如用户的输入。

> 命令有三类来源：用户的动作（提交表单、点击链接）、第三方系统（API、回调通知）、定时器（计划任务）。

> 为什么需要分析命令？分析命令可以对事件的触发源进行分析，从而分析出系统中的角色（包括外部系统、定时器等隐含角色）。

要点：

```
1. 命令是请求，事件是结果；一个命令触发一个事件
2. 三类来源都要列：用户、外部系统、定时器
3. 命令和接口相关，事件和状态变化相关；不要混在一张清单里
4. 命令是权限校验的位置：谁能发、谁不能发
```

在 GOAL 里怎么用：写 AC 的异常场景时，命令清单直接给出“谁不能做”，例如“未登录用户不能提交任务”。

### 事件风暴

> 事件风暴是一种建模的工作坊，一群人在一个屋子里开会，通过头脑风暴的方式将事件通过纸条贴在墙上，通过事件来追溯整个软件当中关键行为发生来确定系统当中状态的变化。找出体现系统状态变化的模型，或者我们可以叫实体，从而分析出我们的整个领域模型，对这些模型的划分，使其满足面向对象的内聚要求，最终得到模块或者服务的划分和映射方式。

> 事件风暴是建立在头脑风暴上的，它的可操作性较低，严重依赖主持人的认知水平，优点则是可以通过“吵架”让咨询师挖掘领域专家和技术专家脑子中真正的业务知识。

参与者通常包括：领域专家、用户研究人员、业务方案设计人员、技术专家、测试专家。一个人做的时候，就是自己扮演这几类角色，把事件一条条写下来。

在 GOAL 里怎么用：事件清单不求好看，求全；先贴、后并、再归类。不要在写事件时争论对错。

### 命令风暴

> 命令风暴接在事件风暴后面：为每个事件找出谁发起了它、需要什么输入、需要什么权限。

命令风暴的产出直接决定三样东西：接口（谁调用）、权限（谁能调）、校验（输入什么算合法）。

在 GOAL 里怎么用：命令清单里“谁不能做”直接变成 AC 的异常场景；“输入什么”直接变成表单校验规则。

### 识别模型

> 从事件与命令里找出承载状态与规则的名词，判断它是实体还是值对象，能不能独立成聚合，聚合根是谁。

这一段在原文里没有单独成章，但事件风暴的产出物就是它：找出体现状态变化的模型，也就是实体，再对这些模型做划分，得到模块或服务。

判断顺序：

```
1. 这个名词有没有 ID、会不会被单独追踪？有 → 实体；没有 → 值对象或属性
2. 它是不是必须和别的东西一起变？是 → 进同一个聚合
3. 这个聚合里谁是唯一入口？那就是聚合根
4. 有没有一个实体被两个聚合共用？有 → 拆开或升级为聚合根
```

### 识别上下文

> 识别上下文是从模型里划出边界：哪些模型必须一起工作、共享一套词；哪些模型虽然同名，但含义不同，必须分开。

做法：拿模型清单，两两比较——同一个词含义不同，切开；同一条事件链从头走到尾，合并；合完检查每个事件是否恰好属于一个领域。

在 GOAL 里怎么用：这一步的产出就是 GOAL 的领域节点，包括“为什么这样切”那行。

### 这套东西的边界

原文对 DDD 的适用性说得很直白，写 GOAL 时也要知道什么时候不该用这么重的做法：

> DDD 最大的局限性是：它不是一个像数据库、操作系统这样特定的技术，而是一种开发思想或者说理念。这就让它变成一门玄学，下限极低，上限极高。

> 使用 DDD 的成本是如此之高，非常不适用于快速做原型验证的项目，也不适合技术复杂性远远大于业务复杂性的项目。

> 可以考虑不要一开始就使用太多 DDD 实践，而是在团队认知负担过高时再来做模型梳理。

对照到我们的模板：GOAL 的五个层级是**最小可用**的建模，不是全套 DDD。原型阶段可以只写目标、领域、REQ、AC，不写聚合；业务复杂到规则互相打架时，再把聚合和术语补上。

原文还给了三条原则，可以当写作时的取舍标准：

> 1. 聚焦核心领域：设计一个应用系统，应该只关注业务的核心问题，其他必要的附属问题应该围绕支撑核心问题来处理。

> 2. 通过协作迭代式探索模型：整个团队中每个人的信息都是局部的，想要建立一个大的图景，自上而下的规划设计在软件开发中是很困难的。

> 3. 使用统一语言：在不同的上下文中不同的名词代表的含义不一样。

翻成写 GOAL 的动作：

```
聚焦核心领域 → 核心子域的规则写最细，支撑子域够用就行，通用子域少写
协作迭代     → GOAL 不是一次写完；每轮发现缺口，回来补，不推翻重来
统一语言     → 每加一个词，先查是否已有定义；有冲突先解决再往下写
```

## 六、一页速查

| 词 | 一句话 | 写 GOAL 时看什么 |
| --- | --- | --- |
| 领域 | 业务知识的集合，由场景构成 | 边界能否一句话说清 |
| 子域 | 核心、支撑、通用 | 这里该投入多少 |
| 领域模型 | 业务概念在程序里的表达 | 是否只保留业务概念 |
| 通用语言 | 同一上下文里一词一义 | 每个词有没有定义 |
| 实体 | 有 ID、有生命周期、要追踪 | 事件里的名词是不是它 |
| 值对象 | 无 ID，改属性即换新值 | 能不能不减实体数量 |
| 聚合 | 必须一起变、一起保证一致 | 哪些东西必须同生共死 |
| 聚合根 | 聚合的唯一入口 | 外部从哪进 |
| 限界上下文 | 一套词、一套规则、一个边界 | 切开还是合并 |
| 事件 | 已发生的状态变化 | 事件链全不全 |
| 命令 | 触发事件的请求 | 谁发起、谁不能做 |
| 事件风暴 | 先贴事件再归类 | 清单是否覆盖全部旅程 |
| 命令风暴 | 为事件找发起者与权限 | 异常场景从哪来 |
| 识别模型 | 找实体、值对象、聚合 | 每个名词有没有归属 |
| 识别上下文 | 划领域边界 | 边界是否互斥 |

## 七、写的时候要守的几条

```
1. 聚合最多两三层，别包太大
2. 分清“关联”和“拥有”：生命周期一致才放进聚合
3. 多对多要问中间模型归谁，例如“成员”归空间
4. 交易类数据锁定当时的快照，别跟着源数据变
5. 核心交易留流水，能对账
6. 业务还在变时先分开，稳定后再统一
7. 重要取舍写进决策记录
```

## 八、检查

`pnpm goal:audit` 查结构，`pnpm goal:trace` 查测试能否追到 AC。规则：

```
A1 目标不写实现方案
A2 每个领域写清边界
A3 每条 REQ 至少一条 AC
A4 AC 不写状态码、字段名
A5 每个领域至少一条异常/边界场景
A6 术语表至少两条
A7 每个领域至少一条 REQ
A8 每个领域写“为什么这样切”
```

## 九、一段完整示例

```
- **目标**：做出能跑、能验、能继续改的应用

  - **认证领域**
    - 事件链：注册 → 登录 → 会话 → 登出
    - 聚合：用户、会话
    - 边界：管身份与会话；不管权限分级、团队成员、找回密码
    - 为什么这样切：账号与会话生命周期一致，合并；权限分级没有多角色需求，砍掉
    - 术语：用户 = 有账号的人；会话 = 一次登录的凭证
    - **REQ-AUTH-001 注册和登录使用邮箱与密码**
      - 来源事件：注册、登录
      - 规则：邮箱密码合法则建立会话，否则拒绝
      - AC-AUTH-001：Given 新用户提交合法邮箱和密码 When 注册 Then 进入工作台
        - **测试用例**：真实浏览器注册 → 通过 ｜ 证据：截图
```
