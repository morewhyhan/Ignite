# v1.0.0：规格闭环从「文档」变成「系统」

## 这份文档要求什么

docs/standards/specification-to-implementation-ddd.md 只讲一件事：
把一个原始需求，经过目标、事实、矛盾、决策、计划、验证，变成可靠的实现，再把验证后的事实写回系统。

它列了 52 条具体要求和 5 个阶段（P0–P5）。这次更新，就是把这 52 条逐条落地。

## 之前的问题

文档写得很完整，但它只是纸面规则：

- 需求写了，计划可以不覆盖全部条件
- 计划建了，可以不说明在解决哪个主要矛盾
- 任务做了，可以没有对应测试
- 测试过了，可以没证明原始目标达成
- 设计写了未来方案，被当成当前事实用
- 同一个组件多个页面各写一遍，结果不一致

一句话：文档存在，约束没有传到代码。

## 这次做了什么

把这 52 条从「要求」变成「机器能检查的东西」：

| 文档要求                 | 现在的落地方式                                       |
| ------------------------ | ---------------------------------------------------- |
| 需求要能被追溯           | 每条 REQ 必须挂 AC，AC 必须能在测试里命名            |
| 计划要覆盖目标与主要矛盾 | 计划缺字段、缺模块路径、缺审查记录，直接进不了 ready |
| 实现前要有失败测试       | 没有真实红灯，不许开始实现                           |
| 完成要有证据             | 当前检查 + 交付审查 + 设计回写，三样齐了才能标 done  |
| 设计要区分事实与目标     | 设计文档必须写状态与来源，缺了报错                   |
| 模块要有自己的验收       | 验收标准必须写所属模块，改坏边界会被拦               |
| 发布要验证最终版本       | release verify 对同一版本跑构建与验收                |

## 现在达到的标准

用文档第 18 节的原话检验：

> 换一个实现者，只读当前有效的文档和代码，他能否知道要达到什么、现在是什么、
> 为什么这样改、改什么、怎样验证、失败后回到哪里？

现在可以回答：能。因为：

- 52 条要求在账本里每条都有结论与理由（全部已完成）
- 每条结论能点到具体计划、检查运行与提交
- 文档里有九步示例，从新建计划走到发布验证

## 与之前的区别（可感知的三点）

1. 以前规则靠自觉，现在规则会拒绝：缺字段、缺红灯、缺回写，命令直接失败。
2. 以前验证要 12 分钟且常被中断，现在 3 分钟跑完，全量测试 2 分 30 秒。
3. 以前文档章节是空的，现在设计文档有真实事件、目录说明有各自职责、段落有来源。

## 还没验证到的

这次落地验证的是文档与规则类改动；还没有用一个真实业务功能（页面、接口、数据）完整走一遍。
也就是说：文档要求的闭环在规则层已成立，在产品开发层还需要一次真实验证。
