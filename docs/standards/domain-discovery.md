# 领域怎么拆

> 文档状态：定稿

## 为什么要记推演

领域不是从代码里长出来的，是从业务里推出来的。只写结果（认证、任务），下一个人（或 Agent）就不知道边界为什么在这，
也无法判断新需求该放哪。所以每次拆领域，必须留下三样：候选、取舍、边界。

方法借鉴 DDD（Eric Evans）与 Event Storming（Alberto Brandolini）：先看业务事件，再找聚合与边界，不是先画模块图。

## 四步

```
1. 列候选   把能想到的业务名词全写下来，不评价
2. 排事件   按用户旅程写出发生了什么（注册、登录、建任务、改任务）
3. 合并拆开 同一条事件链合并；同一个词有两种含义就拆开
4. 定边界   写清管什么、不管什么、砍掉了什么
```

## 判定一个领域是否成立

| 问题                 | 成立的信号                 |
| -------------------- | -------------------------- |
| 有自己的事件链吗     | 从触发到结果能独立讲完     |
| 有独立的词吗         | 这个词在本领域只有一个含义 |
| 边界能被一句话说清吗 | 能写出“只管…不管…”         |
| 有独立的规则吗       | 至少一条 REQ 只属于它      |

四条都答不上来，它就不是领域，是模块或页面。

## 子域类型

| 类型     | 含义                 | 例子                           |
| -------- | -------------------- | ------------------------------ |
| 核心子域 | 产品靠它取胜         | 任务（如果产品核心是任务管理） |
| 支撑子域 | 必须做，但不构成差异 | 认证、计费                     |
| 通用子域 | 买或直接用现成的     | 邮件、存储                     |

类型不写进代码，只写进推演记录，用来决定投入多少。

## 记录模板

写到 `docs/others/notes/domain-reasoning.md`，每条领域一段：

```
### 领域名
- 候选来源：从哪些事件/名词归并来的
- 事件链：触发 → 过程 → 结果
- 为什么合并/切开：
- 边界：管什么 / 不管什么
- 砍掉的想法与原因：
- 通用语言：本领域里每个词只有一个含义
```

## 在 GOAL 里怎么体现

每个领域节点下写四行：

```
- 为什么拆：一句话
- 边界：管…；不管…
- 砍掉：…
- 推演：链接到 notes
```

完整推演不放进 GOAL，GOAL 只留结论与链接。
