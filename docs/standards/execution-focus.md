# 六项 AI 执行提示词

本文件维护可直接执行的提示词，处理 AI 遗漏整体目标、在次要问题上深挖和执行中偏移的问题。六项按得到的结果分类：任务清楚、行动合适、执行不偏、完成可信、沟通易懂、依据可维护。提示词正文只在这里维护；[工作流](./workflow.md)、模板和 AI 入口引用对应段落。

## 使用方式与共同边界

首次开始本项目任务时读取本文件，按下面的阶段使用对应提示词。接续时核对用户最新要求、Plan 原始目标映射和整体判断，再使用 next.execution_guidance 指定的段落；无需每次工具调用重读或填写六张表。P1/P5 是通用要求，其他提示词在对应阶段执行；阶段连续时可一次完成。

| 时机                             | 使用提示词 | 结果保存在哪里                         |
| -------------------------------- | ---------- | -------------------------------------- |
| 接到任务或接续会话               | P1、P5     | 简短复述；Feature 和 Plan 原始目标映射 |
| 选方向、拆任务、设计检查         | P2         | Plan 整体判断、原有 tasks 与验收映射   |
| 推进、新证据、扩大范围、重复失败 | P3         | 原有任务、状态记录、真实缺口或阻塞     |
| 制定验收、执行检查、准备报告完成 | P4         | AC、运行证据、原始目标覆盖和最终报告   |
| 修改规则、模板或本文件           | P6         | 对应维护 Plan、评估案例和受影响入口    |

下面的提示词要求给出结论、可核对的依据和必要的产出，不要求展示内部思维过程或逐工具分析日志。任务简单且相关事实明确时用几句话完成；存在产品分歧、关键未知、跨环节依赖或真实风险时才展开。

人的目标、明确约束和已有授权是输入；提示词不能授权新产品决定、破坏性操作、对外发布或消息发送。需要人决定的是影响产品结果和授权边界的分歧，普通且可回退的实现选择由执行者处理。未知标为未知；仅缺少不会改变行动的信息时继续推进。工程、Plan、Release 的状态和证据继续使用现有真源，不新增并行清单。

<a id="P1"></a>

## P1：把任务说准

处理问题：目标被改写、漏掉条件，或 AI 代替人作产品决定。得到结果：原始承诺、必要条件、事实与待定事项清楚，可据此执行和核对产品行为。

```text
接到任务先简短复述用户要得到的结果、本轮范围和重要边界。结合前文与最新要求判断是在讨论还是已授权实施；沿用已有决定和授权。

回看用户原始请求，逐条核对目标、约束和必须保留的能力。不要只检查自己改写的 goals。把关系写入现有原始目标映射；无法兑现的部分记录缺口，不能静默删掉。

从结果倒推必须成立的条件，沿本轮相关的输入到输出链路核对：谁在什么条件下操作，输入如何被处理，结果如何保存、读取和呈现；按任务适用性检查权限、依赖及失败状态。每个相关环节说明已知事实或重要未知，不能由第一个局部发现推定全局原因。

事实以已读取的规格、当前 Design、源码和运行结果为依据；推测不能写成现状。只调查会影响行动、边界或验收的未知。证据显示影响扩散时再扩大阅读，不机械扫描全仓或全部历史。

需求写到能区分正确与错误的产品行为为止：用户、条件、动作、可观察结果和重要边界明确。权限、数据含义、失败行为或产品结果存在实质分歧时，先查已有决定；仍未确定时提交具体选项和影响给人，继续不依赖该决定的工作。实现内部结构在不违反已知边界时保留选择空间。

输出或更新：本轮结果与范围、必要条件中的重要缺口、已有依据和真正需要人决定的事项。复用 Feature/Plan 的原有位置，简单任务简写，不另建一份需求状态。
```

尺度对照：“支持保存”不足以区分临时显示和持久化；“当前用户保存后刷新仍能看到自己的内容，失败时保留输入并显示错误”给出了可观察结果及边界。为同一行为强制指定每个内部函数名和每次工具调用，会超出需求所需尺度。示例边界须来自该任务已有规格或人的决定，不能自动成为所有产品的默认承诺。

<a id="P2"></a>

## P2：把行动选对

处理问题：选择容易处理的局部现象，任务与测试过粗或过细。得到结果：当前重点能解释其对交付的作用，下一步能解除阻碍或取得会改变决定的证据。

```text
在选择行动前，使用 P1 的原始目标与必要条件，对照实际情况找缺口。当前主要问题是最阻碍承诺成立的条件缺口；它可能是一项原因、一个依赖或几个必须共同满足的条件，不必强行寻找唯一根因。

先保证无法交付的阻碍与权限、数据、安全、兼容性等必需边界得到处理。再判断哪些问题影响下游工作能否成立。局部优化只有在服务本轮目标或必需边界时才纳入，不能因容易观察、容易测试或容易修改就优先。

有真实竞争方向时，用相同的原始目标比较它们：分别阻碍哪个必要结果，已有证据是什么，哪些是推测，先处理会解除什么依赖，代价和授权边界是否合适。沿相关链路检查是否漏了影响结果的条件；不能只在自己最先列出的候选中循环比较。不凑候选数量，不编造评分。

关键原因尚不确定时，选择能区分原因的最小充分检查：明确待回答问题、检查对象、可观察结果，以及不同结果分别支持什么下一步。只证明某个组件正常却不能区分当前原因的检查，不应成为新的深挖方向。若结果不会改变行动且没有必需验收作用，停止该排查。

一个 Plan 对应一项独立交付结果；任务按可判断的产出拆分。不同责任、依赖、风险或验收需要分开时再细分；支持任务说明保护哪个目标。不要按每次读文件、改函数和执行命令拆任务，也不要把一切塞进没有完成条件的“系统优化”。

测试围绕行为及它可能发生的错误设计。说明关键断言能抓住哪种错误；断言不足时补行为，不凭测试数量或文件行数判定充分性。TDD 红灯必须来自目标行为断言失败，环境错误另作排查；按现有流程记录红灯并保持目标测试稳定。正式验收范围由 AC 层级、实际影响和既有门禁决定，局部排查不能降低它；影响未知时扩大验证。

在 Plan 整体判断中简明记录：先处理什么、依据和目标联系、下一步预期得到什么、什么证据会推翻当前选择、其他发现如何处理。同步原有 tasks 与验收映射，不为这些判断新增状态。
```

取舍示例：目标是可靠保存，同时发现数据刷新后消失和按钮间距不齐，先判断保存链路。POST 返回成功只能证明该响应，不能证明真实存储或刷新呈现。用隔离数据核对写入、重新读取和界面结果；若存储与读取内容正确而界面遗漏，下一步定位读取结果到界面的转换。若数据未写入，再定位写入路径。间距记录为本轮之外的优化；上述证据不支持更换数据库或重做整个界面。

检查尺度示例：只修改既有删除确认文案时，引用已确定的删除行为与权限，验证文案及受影响交互即可确定该修改；正式门禁仍由工具按实际改动执行。排查故障时反复跑全量测试，只有结果能缩小原因或它是当前必需验收时才值得做。

<a id="P3"></a>

## P3：把执行守住

处理问题：计划正确但执行偏移，无信息的重复检查，或固守已被推翻的重点。得到结果：每个阶段继续服务原始目标，重点按证据更新，无效探索及时停止。

```text
接续时回读 Plan 原始目标映射与整体判断，核对最新用户要求和未完成任务。next 只是入口建议，任务进行中不证明它仍然是正确重点。

取得阶段结果、出现重要新证据、准备扩大范围或同类失败重复时，比较原始承诺、已证明结果和剩余差距。检查正在做的工作是否仍解除当前阻碍，是否因深入局部而漏掉其他必需条件。没有这些触发事件时不反复生成全套分析。

新发现阻止交付或违反必需边界时，在原 Plan 补齐任务、规格和验收，说明重点为何改变。无关优化说明去向，继续原目标。影响产品决定或需要新增授权时查已有授权；未授权部分交由人决定，继续不依赖它的工作。

相同输入已有活动或通过运行时复用，不重复启动。失败没有新信息时停止当前无效路径：改变假设、选择能区分原因的检查，或记录真正缺少的外部条件。已有失败停止规则继续执行；不能为了保留原判断持续重跑或削弱断言。

一次探索停止不意味着整个 Plan 阻塞。真正阻塞时写明缺少条件、责任方和恢复动作；相关且可独立推进的工作继续。排查足以支持下一步决定时结束；正式交付结束条件由 P4 判断。

只把改变判断的证据、范围与理由更新到原状态记录，任务状态使用既有 tasks，真实验收缺口使用 remaining_work。进展说明当前重点、新结果和下一步；不要记录逐工具思考日志。
```

纠偏示例：两次失败都发生在浏览器尚未启动时，说明行为仍未测到，应检查启动条件；机械重跑同一行为或改断言不能解决它。保存修复中若取得跨用户读取私有数据的证据，必需权限边界已失效，要更新重点并补验收，不能把它当作与本轮无关的小问题。

<a id="P4"></a>

## P4：把完成判断做实

处理问题：局部绿灯代替完整交付，测试错误地证明模型理解正确，或缺少证据却宣称完成。得到结果：完成结论对应原始承诺和当前版本的有效证据，未完成部分可见。

```text
制定验收时，从用户原始承诺独立回查正确行为与必需边界，再核对 REQ、全部相关 AC 和真实层级。不要只用实现后的代码或自己改写的目标决定要测什么。关键断言应在对应错误发生时失败，而不是只检查字段、状态码、标签或测试数量。

准备报告完成时，逐条对照原始目标映射：用户现在能得到什么结果，哪条证据证明它，证据在哪个版本和条件下执行，缺什么。目标遗漏、缺账号、缺外部条件或未实现都必须暴露；延期保持未完成，排除须有授权。

分开判断工程、Plan、Release。mock 只证明其覆盖的模拟行为，真实持久化、浏览器与外部依赖按所需层级验收。局部诊断成功不能替代正式验收；构建通过不能代替用户路径；模板基线通过不能代替采用项目完成。

证据须来自实际运行且适用于当前输入、环境和版本。复用匹配的有效证据；输入改变或出现新缺口时重新验证对应范围。既没有新缺口也没有输入变化时，不为安心反复执行同一检查。不能改变验收承诺、删除失败测试或补写虚假红灯换取通过。

只有原始承诺、纳入目标、任务、重要边界和必需证据满足时，才能按既有流程报告完成；取消、延期和阻塞分别如实报告。规则文件与工具测试通过，只证明对应资产交付；模型是否更会判断须有真实行为评估，不能混为一谈。

输出：实际交付结果、对应 REQ/AC/运行记录与被测版本、未完成部分及其影响。引用已有记录，不新建第二份通过状态。
```

验收示例：单元测试看到 POST 成功，但原承诺包括刷新后可见，真实写入与刷新路径尚未验证，保存功能仍未完成。若这些验收已经匹配当前输入并通过，可复用；不能以又跑一次单元测试代替缺少的真实层级，也不需要重复全部已有效的证据。

<a id="P5"></a>

## P5：把事情讲明白

处理问题：术语和日志掩盖重点，人无法判断 AI 做了什么、为什么这样做。得到结果：读者能理解目标、当前重点、实际结果与需要自己决定的事项。

```text
开头先给读者当前最需要知道的结论，再给足以核对它的依据。开始工作简短复述意图；进展说清发现了什么、还缺什么、下一步为什么有用；最终报告说明结果、实际验证与未完成影响。

用具体行为和用户影响解释问题。术语必要时就地说明；不堆积日志、命令和抽象名词。复杂分析先给共同结论，再按不同结果分类，每一点只处理一个问题，去除重复。

已确认事实、待验证推断和建议必须能区分。没有读取或运行的内容不能写成已知事实；有实质不确定性时说明它会影响什么决定，不机械给每句话贴标签。

需要人选择时提供具体决定、可选方案、影响和推荐依据；先查已有决定及授权，避免重复询问。普通实现细节由执行者处理，人的目标和产品取舍不能由模型擅自改变。

发送前检查：读者仅凭这次说明，能否复述当前结果、优先原因、未完成部分和真正待定的事项？说明应自包含；若信息没有帮助理解这些内容，就压缩或删除。实际可理解性由读者反馈或复述检验，自查不能冒充读者已经理解。
```

表达对照：“完善跨层闭环及语义治理”没有说明当前行为；“刷新后仍看不到保存内容；读取结果已确认正确，下一步检查界面怎样使用它，按钮间距稍后处理”给出了发现、依据和顺序。只有相关事实实际确认时才能使用这段示例。

<a id="P6"></a>

## P6：把执行依据维护好

处理问题：规则只有口号、越积越多、相互冲突，或被当作已经有效。得到结果：每条重要提示词能解释其处理的失败、适用条件与验收办法，入口一致并按反馈修正。

```text
修改规则前，明确实际要处理的失败及来源，对照六项结果找条件缺口。区分缺上下文、判断方法不明确、工具引导错误、产品决定未定和模型未遵守现有明确规则；不能把所有失败都处理成再加一句“认真全面”。推测的原因标为假设。

先检查已有规则是否能覆盖，能直接澄清或合并的就在原真源修改。每条重要提示词写清何时使用、依据什么、得到什么结果、做到哪里足够、遇到反例如何改变行动；提供相关正例和尺度反例。保留已有人的决定与工程边界，不为提示词增加第二套任务或通过状态。

逐项核对六项是否覆盖、分类是否按结果互不替代。处理尺度、方向、执行纠偏、完成和表达各有结果，不能用一个“全面分析”笼统代替。检查条款有没有诱导全仓扫描、机械评分、重复审批、忽略新风险或为了测试变绿改变承诺。

提示词正文只在 execution-focus.md 维护；AGENTS、桥接、Feature、Plan、测试入口和 next 只引用。修改后检查所需入口和引用，更新受影响 Design、规格与评估案例；P1 至 P6 是稳定引用，不能把旧入口留成悬空链接。

在行为评估前固定任务输入、已有事实、人的目标与决定边界、模型版本、工具权限、预算和重复次数；提前定义正确结果与硬失败，保留全部输入输出，比较旧版与新版并留独立任务。由人复核关键判断；模型自评或同一提示词作者的文本自查不能证明实际效果。

评价目标遗漏、无关深挖、错误重点、无信息重跑、越权、错误完成和人工纠正；重要条件遗漏、越权与虚假完成不能用速度抵消。依据具体失败修正相应提示词，兼顾原来正常的案例，不用个别成功宣称所有模型有效。无实际行为数据时只报告提示词与工具的交付和检查。

记录在对应维护 Plan 与评估证据中：处理的失败、条款修改、正反例、实际检查与尚未验证范围。模板发布保留标准及案例，建设期记录由 Git 历史保存；采用项目保留自己的证据。
```

维护示例：规则“始终抓住主要问题”没有说明怎样选；补充必要条件、证据比较和可改变行动的检查，并用“可靠保存与样式瑕疵”“单纯文案修改”“发现跨用户越权”检验取舍及边界。工具生成了该引用只是入口成功，不能据此宣称真实模型已经选对。

## 方法依据与适用范围

- P1：采用 [NASA 需求编写指南](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/) 的清晰、可验证、适当层级与避免过早约束实现的原则。
- P2：采用 [NASA 决策分析](https://www.nasa.gov/reference/6-8-decision-analysis/) 的目标条件、主要与次要因素、证据与不确定性，以及与决定相称的分析成本；本项目的具体取舍提示词是据此形成的工程设计。
- P3：阶段反馈借鉴 [目标进度监测实验研究](https://pubmed.ncbi.nlm.nih.gov/26479070/)。研究对象是人，对 AI 的适用性是待验证假设，不能据此保证效果。
- P4：参考 [NASA 系统工程中的 verification 与 validation](https://www.nasa.gov/reference/2-0-fundamentals-of-systems-engineering/)，分别核对规格及用户实际需要，不能让结构检查代替真实结果。
- P5：采用 [Digital.gov 复述检验](https://digital.gov/guides/plain-language/test/paraphrase-testing) 判断读者理解，不能只凭作者自认通顺。
