# 整体分析与执行取舍

本标准处理同一个问题：AI 在未看清整体目标时钻进局部细节，或在执行中不断偏离。结果应是目标覆盖完整、优先顺序有依据、执行能纠偏。日常状态和证据继续由 [工作流](./workflow.md) 管理。

## 1. 先覆盖整体，再深入局部

接到任务先简短复述目标、预期结果和关键边界。只讨论时保留讨论范围；已获实施授权就继续执行，已有授权不反复询问。

开始实现或接续会话前，先做一次与本轮目标有关的整体梳理：

- 目标覆盖：回看原始请求，检查全部目标、约束和必须保留的能力；沿用 Plan 的原始目标映射，不从自己改写的 goals 反推完整性。
- 关键链路：从用户操作到结果，识别本轮相关的页面、接口、数据、权限、依赖及验收入口。说明哪些环节受影响，哪些已有依据可以沿用；纯文档或工具任务按其输入到输出的链路分析。
- 事实与未知：引用相关 Design、源码或运行结果；把尚未观察的行为、可能原因和缺少的产品决定标为假设或未知。只补查会影响行动或验收的未知。

“全面”以本轮目标和受影响链路为边界。简单且明确的任务用几句话完成梳理；不能机械扫描全仓、阅读全部历史或列出所有想象得到的风险。只有证据显示影响扩散，才扩大阅读和检查范围，并说明原因。

## 2. 选择当前主要问题

在 Plan 的“整体判断与推进顺序”中说明：什么最妨碍本轮目标实现、依据是什么、为什么先处理它、其他发现如何处理。单一明确问题直接说明；有竞争方向时才比较，不能凑固定数量的候选或用没有依据的分数排序。

选择顺序：

1. 先识别无法兑现用户承诺的阻碍，以及权限、数据、安全、兼容性等必须满足的边界；不能为提速忽略这些条件。
2. 沿关键链路寻找决定其他工作能否成立的原因或依赖，优先处理能解除阻碍、验证关键假设的事项。
3. 其他局部优化只有在服务本轮目标或保护必需边界时才纳入；无关优化记录去向，继续当前工作。

主要问题可能是一项依赖，也可能是几个需要一起满足的条件，不必强行归为唯一根因。缺少证据时把判断写成待验证假设；新证据允许更新重点。

## 3. 让颗粒度服从结果

需求写到能确定用户行为、重要结果和相关边界为止：谁、什么条件、做什么、观察到什么。会改变权限、数据或产品结果的不同理解须澄清；内部函数和实现细节保留选择空间。已有决定直接引用，避免重复提问。

一个 Plan 对应一项独立交付结果。任务按可判断的产出拆分；依赖、责任、风险或验证需要分开时再细分。支持任务应说明保护哪个目标或工程边界，不能按每次读文件、改函数、跑命令拆任务，也不能用“优化整个系统”掩盖没有完成条件。

把排查与正式验收分清：

- 排查回答一个影响决策的问题。说明可能原因、下一次检查要区分什么、什么结果支持或推翻判断；若结果不会改变行动，就不继续搜集无关细节。
- 正式验收覆盖全部纳入目标及真实风险，仍按 `ignite check --level auto` 和 Release 规则执行。局部排查成功不替代必需层级；影响不明时保留扩大检查或全量回退。

## 4. 按证据纠偏与停止

完成阶段结果、出现重要新证据、准备扩大范围或重复同类失败时，比较原目标、当前已证明结果和剩余差距。只有这些节点需要补充判断，不记录逐工具思考日志，也不另建任务状态。

| 新发现                                       | 处理方式                                                 |
| -------------------------------------------- | -------------------------------------------------------- |
| 阻止本轮交付或违反必需边界                   | 在原 Plan 内补齐任务、规格或验收，说明为何改变顺序       |
| 改变产品决定、需要新权限或涉及破坏性数据操作 | 先核对已有授权；未授权的决定交由用户，继续不依赖它的工作 |
| 与本轮无关的局部优化                         | 记录待处理去向，不静默扩大范围                           |

相同输入的活动或通过运行按工作流复用。重复失败或探索没有新信息时，停止当前无效路径，修改假设、选择能区分原因的检查，或说明缺少的外部条件；停止一条探索不自动把整个 Plan 标为 blocked。记录真实阻塞和恢复动作，能独立推进的相关工作继续执行。

排查在问题足以支持下一步决定时结束。交付在全部纳入目标和必需证据满足时结束。没有新增缺口或输入变化时，不为了“更放心”重复同一验收；仍缺重要证据时不能以“抓主要矛盾”为由跳过。

## 5. 沟通、复核与规则维护

进展说明发现了什么、还缺什么、下一步为何值得做；结论区分事实、推断和建议。最终报告说明结果、实际验证与未完成部分，用具体行为和影响解释术语。

`next` 的目标、任务和建议用于接续，不能自动判断主要问题，也不能证明自然语言目标无遗漏。进入 ready、扩大范围与宣布完成时，回看 Plan 的整体判断和原始目标映射。工具测试只验证它实际执行的行为；文档结构或关键词通过不证明 AI 的判断质量。

重要规则改动应说明处理的错误、适用条件、预期结果，并在 [执行评估案例](../others/test-cases/execution-focus.md) 中保留对应正例和反例。先验证是否有效，再决定保留、简化或删除；摘要只引用细则，不形成另一套规则。跨模型效果需要固定任务和条件、重复真实执行、保留全部输出，并由人按预先定义的结果判断。

## 尺度示例

| 任务或发现                   | 应怎样判断                                               | 应避免的偏移                                     |
| ---------------------------- | -------------------------------------------------------- | ------------------------------------------------ |
| 刷新后数据消失               | 覆盖写入、真实存储、重新读取和界面呈现，先用证据区分断点 | 没查链路就认定数据库错误，或只反复研究样式       |
| 修改删除确认文案             | 引用现有删除行为和权限，检查本轮文案及相关交互           | 重新设计数据库、强制补架构方案或遍历全部错误状态 |
| 修复中发现能读取他人私有数据 | 判断必需权限边界已受影响，更新重点与对应验收             | 因“本轮只做主问题”忽略真正影响交付的风险         |
| 目标用例已经通过             | 回到全部目标覆盖和正式门禁，复用适用证据                 | 把单例绿色当交付完成，或重复全量测试不产生新信息 |

## 方法依据

需求尺度采用 [NASA 需求编写指南](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/) 的清晰、可验证和适当层级原则。行动取舍采用 [NASA 决策分析](https://www.nasa.gov/reference/6-8-decision-analysis/) 的主要因素、决策成本和信息价值判断。阶段纠偏借鉴 [目标进度监测的实验研究](https://pubmed.ncbi.nlm.nih.gov/26479070/)；该研究对象是人，迁移到 AI 的效果仍需案例评估，不能据此保证所有模型表现。
