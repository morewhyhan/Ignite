# 失败分类与处置

检查、测试或验收未通过时，先分类，再动手。本文是"失败之后去哪、看什么、用什么方法"的入口。

不用本文的后果是可预见的：把同一类失败当成多个独立问题逐个修，修复层层叠加，最终没人说得清系统到底依赖哪些前提。

## 依据

本文不是自创体系。骨架与类目大量借用既有标准与方法，只在最后一节标注本仓库特有部分。

| 体系                                | 借用内容                                                         |
| ----------------------------------- | ---------------------------------------------------------------- |
| IEEE 1044，软件异常分类标准         | 异常记录应区分"症状、缺陷、原因"，以及缺陷所处阶段               |
| ODC，正交缺陷分类（IBM，1992）      | 缺陷类型维度：功能、接口、算法、赋值、检查、时序、构建打包、文档 |
| ISO/IEC 29119，软件测试标准         | 测试过程的缺陷报告与处置                                         |
| Beizer 缺陷分类（1990）             | 功能、结构、数据、集成、系统层                                   |
| ISO/IEC 25010，质量模型             | 性能、可靠性、安全性等质量属性                                   |
| 石川图 6M（人、机、料、法、测、环） | 原因分类的互斥维度                                               |
| 测试 oracle 问题（Weyuker 等）      | 判据本身可能错，判定与被判定要分开                               |
| 约束理论 TOC                        | 系统产出由瓶颈决定；同类问题重复出现说明要改结构                 |
| pstack principle-fix-root-causes    | 复现优先、连问为什么、修模式而非实例                             |
| pstack principle-attack-the-premise | 多个修法共享同一前提且都失败时，攻击前提                         |
| pstack benchmark-checklist          | 性能类结论的可信度检查                                           |

## 金字塔

顶层按"缺陷出在哪一层"三分，互斥且穷尽：产物、验证、运行条件。

```
L0 验收未通过
├─ A 产物缺陷      被检验的对象不符合期望
├─ B 验证缺陷      检验手段给不出可信结论
└─ C 运行条件缺陷  检验无法进行，或结论无效
```

三分判据：换一个检验手段仍失败，落 A；同一个产物在别处能通过，落 B 或 C。

### A 产物缺陷

```
A1 行为与规格不一致      缺行为 / 多行为 / 边界与异常路径
A2 接口与契约不一致      类型签名 / 数据形状 / 兼容性
A3 状态与数据            非法转移 / 并发竞态 / 持久化迁移
A4 质量属性              性能 / 资源 / 安全与权限
A5 文档性产物            规格缺项或矛盾 / 元数据不一致 / 索引引用失效
```

### B 验证缺陷

```
B1 判据错                期望值错 / 断言太松
B2 覆盖不足              该测没测 / 层级不足
B3 测试自身不稳          非确定性 / 顺序依赖 / 设计过重
B4 检查器缺陷            判定逻辑错 / 级别与范围错 / 证据绑定错
```

### C 运行条件缺陷

```
C1 环境                  运行时版本 / 依赖与平台二进制 / 文件系统与操作系统
C2 资源与时间            超时 / 内存句柄 / 并发争用
C3 输入数据              fixture 缺失 / 脏数据 / 外部依赖不可用
C4 流程状态              工作树不干净 / 基线提交错位 / 证据过期
```

## 边界判定

分类最容易错在"看起来像两类"。按顺序匹配，先命中先归属：

| 情形                           | 归属     | 判据                                   |
| ------------------------------ | -------- | -------------------------------------- |
| 用例超时                       | C2       | 单跑在快机器上仍超时则转 B3            |
| 测试设计本身过重               | B3       | 单条用例耗时远超同类，且与数据量无关   |
| 模拟数据库的用例通过但集成失败 | B2       | 低层级通过不等于高层级通过             |
| 文档改动后检查失败             | A5       | 字段互相矛盾归 A5.2，引用不存在归 A5.3 |
| 原本通过的用例被我改红         | A1/A2/A3 | 若报错与"应当报的错"不一致，先怀疑 B4  |
| 环境重装即恢复                 | C1       | 与业务逻辑无关                         |
| 同类失败第二次出现             | 升级     | 不是新类目，是处置升级，见下一节       |

## 各类的处置方法

方法来自该领域的成熟做法，不是逐条修补。

| 类  | 方法                                             | 出处                               |
| --- | ------------------------------------------------ | ---------------------------------- |
| A1  | 先写不变量与契约，再用性质测试覆盖边界           | 契约式设计、property-based testing |
| A2  | 单一真源：类型由 schema 派生，不手写副本         | ISO 25010 可维护性、ODC 接口类     |
| A3  | 把状态摆成转移表，穷举合法与非法转移             | 状态机建模                         |
| A4  | 先测量再优化，用 Amdahl 定律估上限               | 性能工程、benchmark-checklist      |
| A5  | 字段只有出处，没有副本；引用由检查器校验         | 单一真源、本仓库检查器             |
| B1  | 变异测试思路：故意改坏实现，看断言能否抓住       | mutation testing                   |
| B2  | 按 AC 反查测试命名，禁止低层级冒充高层级         | ISO 29119、本仓库 required_layers  |
| B3  | 去除时间、顺序、共享状态依赖；单跑与并发结果一致 | 测试稳定性实践                     |
| B4  | 用历史真实失败样本做门禁回归                     | 检查器自测                         |
| C1  | 固定版本、固定平台、隔离依赖                     | 环境即代码                         |
| C2  | 先测瓶颈再改结构；不做"再试一次"                 | TOC、Amdahl                        |
| C3  | fixture 显式生成与清理，外部依赖可替换           | 测试数据管理                       |
| C4  | 先提交再取证；基线与验证时点对齐                 | 本仓库 Plan 规则                   |

## 处置升级

判据只有一条：

> 同一叶子第二次出现，停止修实例，改这一类。

因为第一次出现可能是意外，第二次说明产生它的结构还在。此时按 pstack principle-attack-the-premise 检查：多个修法是否共享同一个前提，那个前提是否才是问题。

三个可选处置，与 Plan 规则里的超预算处理一致：修这一类、改结构、报卡点。

## 输出格式

一次失败的处置记录至少包含：

```
叶子       A5.2（元数据不一致）
第几次     第二次
影响面     修改会让审查指纹与进度块失效
方法       一次改齐四个字段，再重跑一次
结果       通过 / 未通过，差异原因
```

缺"第几次"就无法判断该修实例还是该改结构；缺"影响面"就会在修完一处后才发现又坏了一处。

## 与既有标准的映射

| 本文叶子      | 对应                         |
| ------------- | ---------------------------- |
| A1 行为       | ODC 功能、Beizer 功能        |
| A2 接口       | ODC 接口                     |
| A3 状态与数据 | ODC 时序、赋值               |
| A4 质量属性   | ISO 25010 性能/可靠性/安全性 |
| A5 文档性     | ODC 文档                     |
| B1 判据       | 测试 oracle 问题             |
| B2 覆盖       | ISO 29119 覆盖要求           |
| B4 检查器     | ODC 检查类（checking）       |
| C1 / C2 / C3  | 6M 的机、法、料              |
| C4 流程       | 6M 的人与流程                |

对不上的地方属于本仓库扩展，见下节。

## 本仓库特有扩展

以下类目在公开标准中没有直接对应，属于本模板的适配：

- **A5.2 元数据不一致**：计划基线、集成提交、审查指纹、进度块互相牵制。
- **A5.3 索引与引用失效**：规格、计划、账本之间的编号引用。
- **C1.3 跨文件系统**：drvfs 与本地盘导致的耗时与超时差异。
- **C4.3 证据过期**：改动使既有检查记录失效。
- **B4.3 证据绑定错**：运行记录与被验证对象不匹配。

这些扩展的共同点是：本模板把"文档与证据"当作产物的一部分，而多数标准只把它们当管理记录。

## 规则编号

- STD-FAIL-101：检查未通过时先归入 A/B/C 叶子，再选该领域的处置方法；未分类的修复不算处置。
- STD-FAIL-102：同一叶子第二次出现时停止修实例，改为修这一类或改结构。
- STD-FAIL-103：处置记录必须写明叶子、第几次、影响面、方法与结果。
