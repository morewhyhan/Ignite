# GOAL 规格

> 文档状态：定稿
>
> **给人和辅助写作的 AI 用。** 本文规定 GOAL 写什么、按什么顺序想清楚、每层必须写清什么。
> 维护流程（每轮怎么读、怎么回写、怎么检查）见 [目标树标准](./goal-tree.md)。

## 一、GOAL 是干什么用的

它是三样东西：

```
1. 需求真源      要什么、做到没有
2. 架构设计载体  领域怎么切、规则挂在哪、为什么这样切
3. 人机接口      人只改这里；Agent 从这里取需求，把结论写回这里
```

它不写：系统现在长什么样（那是 `docs/designs/`）、工程规则（那是 `docs/standards/`）、
逐条测试代码（那是 `tests/` 与 `docs/others/test-cases/`）。

## 二、谁在什么时候用它

| 角色 | 什么时候 | 做什么 |
| --- | --- | --- |
| 人 | 立项、改需求 | 写目标、领域、规则、验收；改完跑 `pnpm goal:audit --record` |
| Agent | 每轮开工前 | 从目标读到用例，找到本轮 REQ 与 AC |
| Agent | 每轮收尾 | 跑测试，把状态与证据写回用例行 |
| 脚本 | 每次状态变化 | 更新汇总与状态，不写内容 |

## 三、五个层级

```
第 1 级  目标        这套软件最终让人完成什么
第 2 级  领域        一块业务边界：一套词、一套规则、一个边界
第 3 级  REQ         这个边界里必须成立的规则
第 4 级  AC          用户做什么、看到什么
第 5 级  测试用例    怎么证明这条 AC 成立
```

### 每级必须写清什么

| 层级 | 必填 | 说明 |
| --- | --- | --- |
| 目标 | 一句话 | 可判定：做到没有能回答 |
| 领域 | 事件链、聚合、边界、为什么这样切、术语 | 见下 |
| REQ | 来源事件、规则 | 规则要能判定真假 |
| AC | Given / When / Then | 用户能观察到的结果 |
| 测试用例 | 怎么测、结果、证据 | 结果写通过或失败 |

领域五个字段的意思：

```
事件链       这个领域里用户做了什么、系统发生了什么
聚合         哪些东西必须一起变化、一起保证一致
边界         管什么、不管什么
为什么这样切  合并或切开的依据
术语         本领域里每个词只有一个含义
```

## 四、按什么顺序写

这十步就是建模的顺序，也是写 GOAL 的顺序：

```
1. 写目标
2. 事件风暴：列事件，用户做了什么、系统发生了什么，先不分类
3. 命令风暴：列命令，每个事件谁发起、要什么输入、要什么权限
4. 识别模型：哪些名词承载状态与规则 → 实体、值对象、聚合、聚合根
5. 识别上下文：同一个词含义不同就切开，同一条事件链就合并 → 得到领域
6. 通用语言：给每个领域定术语，一个词一个含义
7. 写 REQ：从事件与聚合推出规则，标来源事件
8. 写 AC：每条 REQ 拆成可观察的验收
9. 挂用例：每条 AC 写怎么测、结果、证据
10. 回审：事件是否都有着落、边界是否互斥、术语是否一义
```

前六步是想，后四步是写。**写 GOAL 的过程就是建模的过程。**

## 五、写的时候用到的词

| 词 | 意思 | 例子 |
| --- | --- | --- |
| 事件风暴 | 第一步，列领域事件：用户做了什么、系统发生了什么 | 注册成功、任务创建 |
| 命令风暴 | 第二步，列命令：谁发起、要什么输入、要什么权限 | 提交注册表单 |
| 识别模型 | 第三步，从事件与命令里找实体、值对象、聚合、聚合根 | 用户、会话 |
| 识别上下文 | 第四步，按词义与一致性边界切分，得到领域 | 认证、任务 |
| 事件 | 用户做了什么、系统发生了什么 | 用户注册成功 |
| 命令 | 一次操作请求，由谁发起、带什么输入 | 提交注册表单 |
| 实体 | 有身份、有生命周期、会变的东西 | 用户、任务 |
| 值对象 | 没有身份，只由属性决定 | 邮箱、金额 |
| 聚合 | 一组必须一起变化、一起保证一致的东西 | 用户 + 会话 |
| 聚合根 | 外部只能通过它访问聚合内部 | 用户 |
| 领域 | 一套词、一套规则、一个边界 | 认证、任务 |
| 通用语言 | 同一个词在本领域只有一个含义 | “用户”不能有两层意思 |
| 子域类型 | 按重要性分：核心、支撑、通用 | 认证、任务都属支撑 |

## 六、写的时候要守的几条

```
1. 聚合最多两三层，别包太大
2. 分清“关联”和“拥有”：生命周期一致才放进聚合
3. 多对多要问中间模型归谁，例如“成员”归空间
4. 交易类数据锁定当时的快照，别跟着源数据变
5. 核心交易留流水，能对账
6. 业务还在变时先分开，稳定后再统一
7. 重要取舍写进决策记录
```

## 七、检查

`pnpm goal:audit` 查结构，`pnpm goal:trace` 查测试能否追到 AC。规则：

```
A1 目标不写实现方案
A2 每个领域写清边界
A3 每条 REQ 至少一条 AC
A4 AC 不写状态码、字段名
A5 每个领域至少一条异常/边界场景
A6 术语表至少两条
A7 每个领域至少一条 REQ
A8 每个领域写“为什么拆”
```

## 八、一段完整示例

```
- **目标**：做出能跑、能验、能继续改的应用

  - **认证领域**
    - 事件链：注册 → 登录 → 会话 → 登出
    - 聚合：用户、会话
    - 边界：管身份与会话；不管权限分级、团队成员、找回密码
    - 为什么这样切：账号与会话生命周期一致，合并；权限分级没有多角色需求，砍掉
    - 术语：用户 = 有账号的人；会话 = 一次登录的凭证
    - **REQ-AUTH-001 注册和登录使用邮箱与密码**
      - 来源事件：注册、登录
      - 规则：邮箱密码合法则建立会话，否则拒绝
      - AC-AUTH-001：Given 新用户提交合法邮箱和密码 When 注册 Then 进入工作台
        - **测试用例**：真实浏览器注册 → 通过 ｜ 证据：截图
```
