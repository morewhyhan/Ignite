# GOAL 规格

> 文档状态：定稿
>
> **给人和辅助写作的 AI 用。** 本文规定 GOAL 写什么、按什么顺序想清楚、每层必须写清什么。
> 维护流程（每轮怎么读、怎么回写、怎么检查）见 [目标树标准](./goal-tree.md)。

## 一、GOAL 是干什么用的

它是三样东西：

```
1. 需求真源      要什么、做到没有
2. 架构设计载体  领域怎么切、规则挂在哪、为什么这样切
3. 人机接口      人只改这里；Agent 从这里取需求，把结论写回这里
```

它不写：系统现在长什么样（那是 `docs/designs/`）、工程规则（那是 `docs/standards/`）、逐条测试代码（那是 `tests/` 与 `docs/others/test-cases/`）。

## 二、谁在什么时候用它

| 角色 | 什么时候 | 做什么 |
| --- | --- | --- |
| 人 | 立项、改需求 | 写目标、领域、规则、验收；改完跑 `pnpm goal:audit --record` |
| Agent | 每轮开工前 | 从目标读到用例，找到本轮 REQ 与 AC |
| Agent | 每轮收尾 | 跑测试，把状态与证据写回用例行 |
| 脚本 | 每次状态变化 | 更新汇总与状态，不写内容 |

## 三、五个层级

```
第 1 级  目标        这套软件最终让人完成什么
第 2 级  领域        一块业务边界：一套词、一套规则、一个边界
第 3 级  REQ         这个边界里必须成立的规则
第 4 级  AC          用户做什么、看到什么
第 5 级  测试用例    怎么证明这条 AC 成立
```

### 每级必须写清什么

| 层级 | 必填 | 说明 |
| --- | --- | --- |
| 目标 | 一句话 | 可判定：做到没有能回答 |
| 领域 | 事件链、聚合、边界、为什么这样切、术语 | 见下 |
| REQ | 来源事件、规则 | 规则要能判定真假 |
| AC | Given / When / Then | 用户能观察到的结果 |
| 测试用例 | 怎么测、结果、证据 | 结果写通过或失败 |

领域五个字段的意思：

```
事件链       这个领域里用户做了什么、系统发生了什么
聚合         哪些东西必须一起变化、一起保证一致
边界         管什么、不管什么
为什么这样切  合并或切开的依据
术语         本领域里每个词只有一个含义
```

## 四、十个步骤

十个步骤，分四段：想清楚（1–6）、写成规则（7–8）、挂证据（9）、回审（10）。每一步写清：回答什么、输入、产出、约束、完成标准。

| 步 | 名称 | 产出写在哪 | 完成标志 |
| --- | --- | --- | --- |
| 1 | 写目标 | GOAL 第 1 级 | 能回答做到没有 |
| 2 | 事件风暴 | 事件清单 | 覆盖全部用户旅程 |
| 3 | 命令风暴 | 命令清单 | 每个事件都有发起者与输入 |
| 4 | 识别模型 | 实体、值对象、聚合、聚合根 | 每个名词都有归属 |
| 5 | 识别上下文 | 领域 | 边界互斥、事件都有归属 |
| 6 | 通用语言 | 术语表 | 一词一义 |
| 7 | 写 REQ | GOAL 第 3 级 | 每条能判定真假 |
| 8 | 写 AC | GOAL 第 4 级 | 用户能观察到 |
| 9 | 挂用例 | GOAL 第 5 级 | 有结果与证据 |
| 10 | 回审 | 修订记录 | 两项检查全过 |

### 第 1 步 写目标

- 回答：这套软件最终让人完成什么。
- 输入：用户的原始诉求，尽量保留原话。
- 产出：GOAL 第 1 级，一句话。
- 约束：
  - 不写技术方案。原文的说法是：先把业务逻辑建模，再完成技术实现；技术细节无非是响应用户操作和持久化模型。
  - 不写“支持、优化、完善”这类无法判定的词。
  - 一句话内说完，不举例子、不列功能。
- 完成标准：换一个人读，能回答“做到没有”。

### 第 2 步 事件风暴

- 回答：用户做了什么、系统发生了什么。
- 输入：目标、用户旅程、现有页面或流程。
- 产出：事件清单，一行一个，用过去式（注册成功、任务创建、登出完成）。
- 约束：
  - 先不分类、不评价、不合并。原文的做法是：把事件写在纸条上贴到墙上，通过事件追溯关键行为，确定系统状态的变化。
  - 只写用户能感知的事实，不写“系统调用数据库”这种内部动作。
  - 一个事件只描述一件事，不把“注册并登录”写成一条。
  - 想不清楚时，原文给的办法是：把“电”断掉，假装自己是服务员，用纸和笔把流程走一遍。
- 完成标准：每条用户旅程都能在清单里从头走到尾。

### 第 3 步 命令风暴

- 回答：每个事件由谁发起、要什么输入、要什么权限。
- 输入：事件清单。
- 产出：命令清单，一行一个命令，标注发起者、输入、权限。
- 约束：
  - 一个命令对应一个事件；命令是“请求”，事件是“已经发生”。
  - 权限要写“谁不能做”，不写“支持权限控制”。
  - 系统内部的定时任务不是用户命令，单独标注。
- 完成标准：每个事件都能找到发起它的命令；每个命令都能说出被拒绝的条件。

### 第 4 步 识别模型

- 回答：哪些名词承载状态与规则。
- 输入：事件与命令清单。
- 产出：实体、值对象、聚合、聚合根。
- 约束：
  - 有身份、会变的才叫实体；只由属性决定的是值对象。原文的例子：银行账户有 ID，币种和余额变了还是同一个账户；交易单里的金额由币种和数值组成，改任何一个，金额就不再是原来那个。
  - 一组必须一起变化、一起保证一致的东西放进聚合，聚合有且只有一个聚合根；要管理聚合必须通过聚合根。
  - 聚合最多两三层；分清“关联”和“拥有”，生命周期不一致的不要放进聚合；多对多要问中间模型归谁。
  - 一个实体可以独立作为一个聚合。
- 完成标准：事件里出现的每个名词都有归属；每个聚合能一句话说清它保证什么一致。

### 第 5 步 识别上下文

- 回答：这些模型该怎么切成领域。
- 输入：模型清单与事件链。
- 产出：领域清单，每个领域一段。
- 约束：
  - 同一个词在两处含义不同就切开。原文的例子：商品在物流、交易、支付里含义完全不一样，它们处在不同上下文。
  - 同一条事件链就合并；一个领域只回答一类问题。
  - 领域是问题，上下文是解。原文的说法是：领域导出上下文，上下文支撑领域；不是包含关系。
  - 领域按重要性分三类：核心域（对业务极其重要）、支撑域（支持重要业务，比如登录、找回密码）、通用域（已经成为相对独立的支撑，比如实名验证、人机校验）。
  - 切完要能写出“管什么、不管什么”。
- 完成标准：每个事件恰好属于一个领域；任意两个领域的边界不重叠。

### 第 6 步 通用语言

- 回答：每个领域里的词到底是什么意思。
- 输入：领域清单。
- 产出：术语表，一行一个词。
- 约束：
  - 一个词只在一个领域里有一个含义；同义词只留一个。
  - 原文的定义：通用语言是业务人员和开发人员使用无歧义的统一语言来对话，包括对概念的统一理解和定义。
  - 不用“等等、相关、其他”这类模糊词。
  - 词要写进 GOAL 的领域节点，不另建词表。
- 完成标准：把术语表给一个新读者，他能用这些词复述领域规则而不产生歧义。

### 第 7 步 写 REQ

- 回答：这个领域里哪条规则必须成立。
- 输入：事件、命令、聚合。
- 产出：GOAL 第 3 级，每条 REQ 带来源事件。
- 约束：
  - 一条 REQ 只写一条规则；能判定真假。
  - 不写实现方式：不写接口、字段、状态码。
  - 必须能指回至少一个事件；指不回去的规则，要么事件漏了，要么规则是臆想的。
- 完成标准：每条 REQ 都能举出一个违反它的真实场景。

### 第 8 步 写 AC

- 回答：用户做什么、看到什么，才算这条规则成立。
- 输入：REQ。
- 产出：GOAL 第 4 级，Given / When / Then。
- 约束：
  - 只写用户能观察到的结果；不写状态码、字段名、内部调用。
  - 至少覆盖一条异常或边界。
  - 一条 REQ 可以有多条 AC；一条 AC 只证明一条 REQ。
- 完成标准：把 AC 交给测试人员，他能写出测试而不用再问。

### 第 9 步 挂用例

- 回答：怎么证明这条 AC 成立。
- 输入：AC。
- 产出：GOAL 第 5 级，一条用例一行，带结果与证据。
- 约束：
  - 一条 AC 至少一条用例；浏览器类必须截图。
  - 结果只能写通过或失败，不写“基本可用”。
  - 证据要能打开：运行日志或截图。
- 完成标准：点开用例行，能看到测了什么、结果、证据在哪。

### 第 10 步 回审

- 回答：前面九步有没有漏、有没有打架。
- 输入：整份 GOAL。
- 产出：修订后的 GOAL 与审计记录。
- 约束：
  - 事件必须都有归属；领域边界必须互斥；每个词只能一个含义。
  - 改完必须重跑审计并记录，记录绑当前 GOAL。
- 完成标准：`pnpm goal:audit` 与 `pnpm goal:trace` 都通过。

前六步是想，后四步是写。**写 GOAL 的过程就是建模的过程。**

## 五、这些词到底是什么意思

### 领域

> 领域是软件要解决的业务问题和诉求。通俗来说，领域就是业务需求。

> 领域是业务相关知识的集合。构成领域的要素就是特定的业务场景。

用的时候：先找业务场景，再把场景归类。一个领域里只有一类问题，能一句话说清“管什么、不管什么”。

反例：把“认证”和“权限”写成同一个领域——它们的场景不同，词义也不同。

### 子域

> 通过对业务的场景划分，再对其分类，就是我们的子域。

| 类型 | 原文定义 | 例子 |
| --- | --- | --- |
| 核心域 | 对业务极其重要的场景 | 内容社区里的提问、看帖、回复 |
| 支撑域 | 对重要业务支持的场景 | 登录、找回密码 |
| 通用域 | 已成为相对独立的支撑业务场景 | 实名验证、人机校验 |

用的时候：类型不写进代码，只决定投入多少。核心域认真做，支撑域够用就行，通用域优先用现成的。

### 领域模型

> 领域模型是业务概念在程序中的一种表达方式。模型是用来设计和理解整个软件结构，切记不要事无巨细的模型。

用的时候：模型只保留业务概念，不追求字段齐全。能回答业务问题就够，不为了“以后可能用到”加字段。

### 通用语言

> 通用语言是指在软件设计中，业务人员和开发人员需要使用无歧义的统一语言来对话。

用的时候：每个词在 GOAL 的领域节点里定义一次；同一个词换个领域要么换词，要么明确写“这里指什么”。

反例：同一个“用户”，在认证里指“有账号的人”，在任务里指“任务的所有者”，却都写“用户”。

### 实体

> 实体是领域模型面向对象语言的具体体现，一般是一个类。

> 实体可以使用 ID 标识。

用的时候：有身份、会变化、需要追踪的，才是实体。

例子：用户、任务、订单。

### 值对象

> 值对象是一种特殊的实体，但一般认为没有自己的状态和生命周期。值对象是用属性标识，任何属性的变化都视为新的对象。

例子：金额由币种和数值组成，改任何一个，金额就不再是原来那个。

用的时候：不需要单独追踪、只关心值的，做成值对象，不要给它 ID。

### 聚合与聚合根

> 聚合是一组生命周期一致的实体集合，表达统一的业务意义。聚合的意义在于让业务统一、一致。

> 聚合根是聚合中最核心的对象，是聚合的领航员。要管理聚合必须使用一个聚合根。聚合中有且只有一个聚合根，一个实体可以独立作为一个聚合。

用的时候：

```
1. 先问：这些东西是不是必须一起变、一起保证一致？是，才放进同一个聚合
2. 生命周期不一致的，用关联，不要用拥有
3. 外部只能通过聚合根访问内部
4. 聚合最多两三层，别包太大
5. 多对多关系要问：中间那个东西归谁（例如“成员”归空间）
```

反例：把“开户申请”塞进“账户”聚合——申请的生命周期和账户不一致，应该关联而不是拥有。

### 限界上下文

> 限界上下文是有统一业务目标和概念的聚合组成的集合。大型项目都会存在多种模型，这些模型在不同的上下文中，可能有相似业务概念，但是他们的业务目标完全不一样。

> 识别上下文可以从概念的二义性着手，比如商品的概念在物流、交易、支付含义完全不一样。

用的时候：这里的“领域”就是限界上下文——一套词、一套规则、一个边界。切开还是合并，看两件事：

```
同一个词，两个地方含义不同 → 切开
同一条事件链，从头走到尾     → 合并
```

### 事件与命令

> 事件：系统状态已经发生的变化；命令：让系统发生变化的请求。

用的时候：事件用过去式（注册成功），命令用动词（提交注册）。一个命令触发一个事件，一个事件可能由多个命令引起。

### 事件风暴

> 事件风暴是一种建模的工作坊：一群人通过头脑风暴，把事件写在纸条上贴到墙上，通过事件追溯关键行为，确定系统状态的变化，找出体现状态变化的模型，最终得到模块或服务的划分。

用的时候：先贴事件，不争论对错；贴完再归类。一个人做时，就是拿一张纸，把用户旅程里发生的事一条条写下来。

### 命令风暴

> 命令风暴接在事件风暴后面：为每个事件找出谁发起了它、需要什么输入、需要什么权限。

用的时候：命令清单是权限与校验的来源。写不出命令的事件，多半是系统内部动作，不是用户行为。

### 识别模型

> 从事件与命令里找出承载状态与规则的名词，判断它是实体还是值对象，能不能独立成聚合，聚合根是谁。

用的时候：事件里每个名词都要有归属；没有归属的名词，要么补模型，要么说明它只是描述。

### 识别上下文

> 识别上下文是从模型里划出边界：哪些模型必须一起工作、共享一套词；哪些模型虽然同名，但含义不同，必须分开。

用的时候：划完必须能写出每个领域的“管什么、不管什么”，并且任意两个领域的边界不重叠。

## 六、写的时候要守的几条

```
1. 聚合最多两三层，别包太大
2. 分清“关联”和“拥有”：生命周期一致才放进聚合
3. 多对多要问中间模型归谁，例如“成员”归空间
4. 交易类数据锁定当时的快照，别跟着源数据变
5. 核心交易留流水，能对账
6. 业务还在变时先分开，稳定后再统一
7. 重要取舍写进决策记录
```

## 七、检查

`pnpm goal:audit` 查结构，`pnpm goal:trace` 查测试能否追到 AC。规则：

```
A1 目标不写实现方案
A2 每个领域写清边界
A3 每条 REQ 至少一条 AC
A4 AC 不写状态码、字段名
A5 每个领域至少一条异常/边界场景
A6 术语表至少两条
A7 每个领域至少一条 REQ
A8 每个领域写“为什么这样切”
```

## 八、一段完整示例

```
- **目标**：做出能跑、能验、能继续改的应用

  - **认证领域**
    - 事件链：注册 → 登录 → 会话 → 登出
    - 聚合：用户、会话
    - 边界：管身份与会话；不管权限分级、团队成员、找回密码
    - 为什么这样切：账号与会话生命周期一致，合并；权限分级没有多角色需求，砍掉
    - 术语：用户 = 有账号的人；会话 = 一次登录的凭证
    - **REQ-AUTH-001 注册和登录使用邮箱与密码**
      - 来源事件：注册、登录
      - 规则：邮箱密码合法则建立会话，否则拒绝
      - AC-AUTH-001：Given 新用户提交合法邮箱和密码 When 注册 Then 进入工作台
        - **测试用例**：真实浏览器注册 → 通过 ｜ 证据：截图
```
