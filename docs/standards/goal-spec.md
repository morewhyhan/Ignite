# GOAL 规格

> 文档状态：定稿
>
> **给人和辅助写作的 AI 用。** 本文规定 GOAL 写什么、按什么顺序想清楚、每层必须写清什么。
> 维护流程（每轮怎么读、怎么回写、怎么检查）见 [目标树标准](./goal-tree.md)。

## 一、GOAL 是干什么用的

它是三样东西：

```
1. 需求真源      要什么、做到没有
2. 架构设计载体  领域怎么切、规则挂在哪、为什么这样切
3. 人机接口      人只改这里；Agent 从这里取需求，把结论写回这里
```

它不写：系统现在长什么样（那是 `docs/designs/`）、工程规则（那是 `docs/standards/`）、
逐条测试代码（那是 `tests/` 与 `docs/others/test-cases/`）。

## 二、谁在什么时候用它

| 角色 | 什么时候 | 做什么 |
| --- | --- | --- |
| 人 | 立项、改需求 | 写目标、领域、规则、验收；改完跑 `pnpm goal:audit --record` |
| Agent | 每轮开工前 | 从目标读到用例，找到本轮 REQ 与 AC |
| Agent | 每轮收尾 | 跑测试，把状态与证据写回用例行 |
| 脚本 | 每次状态变化 | 更新汇总与状态，不写内容 |

## 三、五个层级

```
第 1 级  目标        这套软件最终让人完成什么
第 2 级  领域        一块业务边界：一套词、一套规则、一个边界
第 3 级  REQ         这个边界里必须成立的规则
第 4 级  AC          用户做什么、看到什么
第 5 级  测试用例    怎么证明这条 AC 成立
```

### 每级必须写清什么

| 层级 | 必填 | 说明 |
| --- | --- | --- |
| 目标 | 一句话 | 可判定：做到没有能回答 |
| 领域 | 事件链、聚合、边界、为什么这样切、术语 | 见下 |
| REQ | 来源事件、规则 | 规则要能判定真假 |
| AC | Given / When / Then | 用户能观察到的结果 |
| 测试用例 | 怎么测、结果、证据 | 结果写通过或失败 |

领域五个字段的意思：

```
事件链       这个领域里用户做了什么、系统发生了什么
聚合         哪些东西必须一起变化、一起保证一致
边界         管什么、不管什么
为什么这样切  合并或切开的依据
术语         本领域里每个词只有一个含义
```

## 四、按什么顺序写

十个步骤，分四段：想清楚（1–6）、写成规则（7–8）、挂证据（9）、回审（10）。
每一步都写清：回答什么、输入、产出、约束、完成标准。

| 步 | 名称 | 产出写在哪 | 完成标志 |
| --- | --- | --- | --- |
| 1 | 写目标 | GOAL 第 1 级 | 能回答做到没有 |
| 2 | 事件风暴 | 事件清单 | 覆盖全部用户旅程 |
| 3 | 命令风暴 | 命令清单 | 每个事件都有发起者与输入 |
| 4 | 识别模型 | 实体、值对象、聚合、聚合根 | 每个名词都有归属 |
| 5 | 识别上下文 | 领域 | 边界互斥、事件都有归属 |
| 6 | 通用语言 | 术语表 | 一词一义 |
| 7 | 写 REQ | GOAL 第 3 级 | 每条能判定真假 |
| 8 | 写 AC | GOAL 第 4 级 | 用户能观察到 |
| 9 | 挂用例 | GOAL 第 5 级 | 有结果与证据 |
| 10 | 回审 | 修订记录 | 四项检查全过 |

### 第 1 步 写目标

- 回答：这套软件最终让人完成什么。
- 输入：用户的原始诉求，尽量用原话。
- 产出：GOAL 第 1 级，一句话。
- 约束：不写技术方案；不写“支持、优化、完善”这类无法判定的词；一句话内说完。
- 完成标准：换一个人读，能回答“做到没有”。

### 第 2 步 事件风暴

- 回答：用户做了什么、系统发生了什么。
- 输入：目标、用户旅程、现有页面或流程。
- 产出：事件清单，一行一个，用过去式（注册成功、任务创建、登出完成）。
- 约束：先不分类、不评价、不合并；只写用户能感知的事实；一个事件只描述一件事。
- 完成标准：每条用户旅程都能在清单里从头走到尾。

### 第 3 步 命令风暴

- 回答：每个事件由谁发起、要什么输入、要什么权限。
- 输入：事件清单。
- 产出：命令清单，一行一个命令，标注发起者、输入、权限。
- 约束：一个命令对应一个事件；权限要写“谁不能做”；不把系统内部定时任务写成用户命令。
- 完成标准：每个事件都能找到发起它的命令；每个命令都能说出被拒绝的条件。

### 第 4 步 识别模型

- 回答：哪些名词承载状态与规则。
- 输入：事件与命令清单。
- 产出：实体、值对象、聚合、聚合根。
- 约束：有身份、会变的才叫实体；只由属性决定的是值对象；一组必须一起变化的放进聚合，入口只能有一个聚合根；聚合不超过两三层；分清“关联”和“拥有”，生命周期不一致的不要放进聚合。
- 完成标准：事件里出现的每个名词都有归属；每个聚合能一句话说清它保证什么一致。

### 第 5 步 识别上下文

- 回答：这些模型该怎么切成领域。
- 输入：模型清单与事件链。
- 产出：领域清单，每个领域一段。
- 约束：同一个词在两处含义不同就切开；同一条事件链就合并；一个领域只回答一类问题；切完要能写出“管什么、不管什么”。
- 完成标准：每个事件恰好属于一个领域；任意两个领域的边界不重叠。

### 第 6 步 通用语言

- 回答：每个领域里的词到底是什么意思。
- 输入：领域清单。
- 产出：术语表，一行一个词。
- 约束：一个词只在一个领域里有一个含义；同义词只留一个；不用“等等、相关、其他”这类模糊词。
- 完成标准：把术语表给一个新读者，他能用这些词复述领域规则而不产生歧义。

### 第 7 步 写 REQ

- 回答：这个领域里哪条规则必须成立。
- 输入：事件、命令、聚合。
- 产出：GOAL 第 3 级，每条 REQ 带来源事件。
- 约束：一条 REQ 只写一条规则；能判定真假；不写实现方式（不写接口、字段、状态码）；必须能指回至少一个事件。
- 完成标准：每条 REQ 都能举出一个违反它的真实场景。

### 第 8 步 写 AC

- 回答：用户做什么、看到什么，才算这条规则成立。
- 输入：REQ。
- 产出：GOAL 第 4 级，Given / When / Then。
- 约束：只写用户能观察到的结果；不写状态码、字段名、内部调用；至少覆盖一条异常或边界；一条 REQ 可以有多条 AC。
- 完成标准：把 AC 交给测试人员，他能写出测试而不用再问。

### 第 9 步 挂用例

- 回答：怎么证明这条 AC 成立。
- 输入：AC。
- 产出：GOAL 第 5 级，一条用例一行，带结果与证据。
- 约束：一条 AC 至少一条用例；浏览器类必须截图；结果只能写通过或失败；证据要能打开。
- 完成标准：点开用例行，能看到测了什么、结果、证据在哪。

### 第 10 步 回审

- 回答：前面九步有没有漏、有没有打架。
- 输入：整份 GOAL。
- 产出：修订后的 GOAL 与审计记录。
- 约束：事件必须都有归属；领域边界必须互斥；每个词只能一个含义；改完必须重跑审计并记录。
- 完成标准：`pnpm goal:audit` 与 `pnpm goal:trace` 都通过，且记录绑当前 GOAL。

前六步是想，后四步是写。**写 GOAL 的过程就是建模的过程。**

## 五、写的时候用到的词

| 词 | 意思 | 例子 |
| --- | --- | --- |
| 事件风暴 | 第一步，列领域事件：用户做了什么、系统发生了什么 | 注册成功、任务创建 |
| 命令风暴 | 第二步，列命令：谁发起、要什么输入、要什么权限 | 提交注册表单 |
| 识别模型 | 第三步，从事件与命令里找实体、值对象、聚合、聚合根 | 用户、会话 |
| 识别上下文 | 第四步，按词义与一致性边界切分，得到领域 | 认证、任务 |
| 事件 | 用户做了什么、系统发生了什么 | 用户注册成功 |
| 命令 | 一次操作请求，由谁发起、带什么输入 | 提交注册表单 |
| 实体 | 有身份、有生命周期、会变的东西 | 用户、任务 |
| 值对象 | 没有身份，只由属性决定 | 邮箱、金额 |
| 聚合 | 一组必须一起变化、一起保证一致的东西 | 用户 + 会话 |
| 聚合根 | 外部只能通过它访问聚合内部 | 用户 |
| 领域 | 一套词、一套规则、一个边界 | 认证、任务 |
| 通用语言 | 同一个词在本领域只有一个含义 | “用户”不能有两层意思 |
| 子域类型 | 按重要性分：核心、支撑、通用 | 认证、任务都属支撑 |

## 六、写的时候要守的几条

```
1. 聚合最多两三层，别包太大
2. 分清“关联”和“拥有”：生命周期一致才放进聚合
3. 多对多要问中间模型归谁，例如“成员”归空间
4. 交易类数据锁定当时的快照，别跟着源数据变
5. 核心交易留流水，能对账
6. 业务还在变时先分开，稳定后再统一
7. 重要取舍写进决策记录
```

## 七、检查

`pnpm goal:audit` 查结构，`pnpm goal:trace` 查测试能否追到 AC。规则：

```
A1 目标不写实现方案
A2 每个领域写清边界
A3 每条 REQ 至少一条 AC
A4 AC 不写状态码、字段名
A5 每个领域至少一条异常/边界场景
A6 术语表至少两条
A7 每个领域至少一条 REQ
A8 每个领域写“为什么拆”
```

## 八、一段完整示例

```
- **目标**：做出能跑、能验、能继续改的应用

  - **认证领域**
    - 事件链：注册 → 登录 → 会话 → 登出
    - 聚合：用户、会话
    - 边界：管身份与会话；不管权限分级、团队成员、找回密码
    - 为什么这样切：账号与会话生命周期一致，合并；权限分级没有多角色需求，砍掉
    - 术语：用户 = 有账号的人；会话 = 一次登录的凭证
    - **REQ-AUTH-001 注册和登录使用邮箱与密码**
      - 来源事件：注册、登录
      - 规则：邮箱密码合法则建立会话，否则拒绝
      - AC-AUTH-001：Given 新用户提交合法邮箱和密码 When 注册 Then 进入工作台
        - **测试用例**：真实浏览器注册 → 通过 ｜ 证据：截图
```
