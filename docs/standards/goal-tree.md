# 目标树标准

> 文档状态：定稿

- STD-GOAL-101：目标树是 AI 每轮开工前的唯一阅读入口，只做目录，细节链接到 docs/ 对应位置。

## 这份标准管什么

目标树是每一次开发前必读的根源：它声明目标、领域、规则与验收，不解释系统全貌。项目现状看 `docs/designs/`，使用说明看 `docs/README.md`，规则看 `docs/standards/`。它是开发的起点，不是项目理解的全部。

## 六层

| 层   | 回答的问题                                       | 放在哪里                                            |
| ---- | ------------------------------------------------ | --------------------------------------------------- |
| 目标 | 这套软件最终让人完成什么                         | `GOAL.md`                                           |
| 领域 | 要达成目标，必须先有哪几块业务边界               | `GOAL.md` + `docs/designs/domain.md`                |
| REQ  | 这个边界里哪条规则必须成立                       | `GOAL.md` + `docs/features/<domain>.md`             |
| 场景 | 这条规则在正常、边界、异常、权限、并发下分别怎样 | `docs/features/<domain>.md`                         |
| AC   | 用户做什么、看到什么                             | `GOAL.md` 一句话 + Feature 里的完整 Given/When/Then |
| 测试 | 怎么证明                                         | `tests/`，标题带 `[AC-编号]`                        |

## 怎么写

1. 写目标：一句话，允许模糊。
2. 事件风暴：按角色列“现实里会发生什么”，每条是“谁 + 遇到什么 + 状态变成什么”。
3. 从事件归并领域：同一个词含义不同 → 分成两个领域；同一条事件链 → 同一个领域。
4. 每个事件问一句“系统必须保证什么” → 得到一条 REQ。
5. 每条 REQ 铺场景：正常、边界、异常、权限、并发与重复提交。
6. 场景写成 AC：Given 前提，When 用户动作，Then 看到什么。
7. 每条 AC 挂一条测试，标题带编号，层级按真实路径标。

## 三条硬约束

```
1. 每个节点只有一个父节点
2. 编号不复用：REQ-<域>-NNN、AC-<域>-NNN
3. 每个节点都是必要不充分条件：缺了它不行，有它不保证上层成立
```

## 链接规则

目标树与其余文档按五层挂接，每层只回答自己的问题：

| 层   | 位置                        | 与树的关系                                                                |
| ---- | --------------------------- | ------------------------------------------------------------------------- |
| 需求 | `docs/features/<domain>.md` | REQ 与 AC 的完整背景、场景、边界；与 `GOAL.md` 双向同步                   |
| 设计 | `docs/designs/`             | 当前事实：字段、接口、页面；文末回链它服务的 REQ 编号                     |
| 标准 | `docs/standards/`           | 技术红线：目录、错误格式、测试要求；树不重复这些规则                      |
| 决策 | `docs/others/adr/`          | 贵且不可逆的选择；写清影响了哪些 REQ                                      |
| 验证 | `tests/`                    | 每条 AC 至少一条测试，标题带 `[AC-编号]`；按层放（e2e / contracts / api） |

### 同步规则

- AC 的完整内容在 `GOAL.md` 与 `docs/features/<domain>.md` 各写一份，编号与 Given/When/Then 必须一致。
- 设计文档末尾必须回链它服务的 REQ 编号，保证设计层与需求层同步。
- 链接用相对路径，指向真实文件；断链视为树写错。
- 测试按层放，不按领域放；测试标题里带 `[AC-编号]`。

## 执行顺序（每轮固定）

    1. 读 GOAL.md，确认本次要动的 REQ / AC
    2. 读该 REQ 链接的 Feature：背景、场景、边界、反例
    3. 读该领域链接的 Design：现在是什么（字段、接口、页面）
    4. 改代码与测试
    5. 回写：Design 更新、AC 链接补上
    6. 报告：动了哪条 REQ/AC、改了哪些文件、跑了什么、结果如何

每一步都对应一个可见状态，人类随时知道执行到第几步。不要跳过第 1 步直接看代码，也不要读完 GOAL 就不看 Feature 与 Design。

## 失败分流

跑不通时先判断是哪一类，再决定回到哪里：

| 判断                        | 现象                                | 回到哪里                                     |
| --------------------------- | ----------------------------------- | -------------------------------------------- |
| A. 实现或文档的 bug         | AC 写清了期望，实现或测试不符       | 五层文档：docs/features、docs/designs、tests |
| B. 需求没说清 / 矛盾 / 缺失 | AC 不存在、两条 AC 冲突、场景没覆盖 | GOAL.md，由人类补；AI 不得自行改需求         |

判断依据只有一条：AC 里的期望是否存在且自洽。

## 缺口清单（B 类必须给，不许自行决定）

    缺在哪：REQ/AC 编号，或无对应节点
    现象：实际发生了什么
    影响：不补会怎样
    建议：补一条什么

给了清单就停，等人类补 GOAL 后再继续。

## 当前步骤的表达

每轮报告开头写一行：

    步骤：3/6  正在读 designs/students.md
    REQ：REQ-STUDENT-003   AC：AC-STUDENT-007

人类据此知道执行到哪一步、动的是哪条需求。

## 进度看板

GOAL.md 顶部两块由工具生成/更新，不要手改：

    进度表  pnpm goal:status        读测试文件，标出 缺测试 / 测试缺编号 / 有测试
    验证    pnpm goal:status --run  真的跑这些测试，标出 已验证 / 失败，并记时间
    当前    <!-- goal-current -->   执行者每轮更新：步骤 n/6 · REQ · AC

人打开 GOAL.md 就能看到：做到哪一条、有没有测试、验证过没有、正在做哪一步。

### 证据怎么记

| 验证层 | 证据形式             | 怎么写入                                           |
| ------ | -------------------- | -------------------------------------------------- |
| 浏览器 | 截图                 | 存 docs/others/evidence/<AC-ID>/<日期>.png，再登记 |
| 接口   | 响应片段或 curl 输出 | 存同目录 <日期>.txt                                |
| 数据库 | 查询结果或迁移输出   | 存同目录 <日期>.sql.txt                            |
| 单元   | 测试输出与运行时间   | --run 自动记入状态表                               |

登记命令：

    pnpm goal:status --evidence AC-STUDENT-007 docs/others/evidence/AC-STUDENT-007/2026-11-08.png

它把 证据：链接 追加到该 AC 的说明行，之后 --run 只负责标已验证与时间。截图与文本都进仓库，可追溯，不靠口头。

### 截图怎么来

    1. pnpm test:e2e 跑相关用例
    2. 把浏览器截图存 docs/others/evidence/<AC-ID>/<日期>.png
    3. pnpm goal:status --evidence <AC-ID> docs/others/evidence/<AC-ID>/<日期>.png

浏览器类 AC（tests/e2e/）必须有图片证据，否则状态显示 缺截图；其它层的 --run 会自动写入运行日志并用它作证据。

## 叶子的颗粒度

一条 AC 只装一个用户动作和一个可见结果：

    好：Given 未登录，When 打开工作台，Then 被带回首页
    太细：断言 session 对象被写入（这是实现）
    太粗：注册并登录后进入工作台（两个动作，拆两条）

判断标准：写不出“用户做了什么、看到什么”，就不是 AC。
一条 REQ 通常 1–5 条 AC；超过说明这条 REQ 太大，拆 REQ，不要继续拆 AC。
树可以很大，但叶子必须一样细——细到动作与可见结果为止。

## 测试说明必须回答四问

    场景：谁在什么情况下
    通过：用户能感知到什么变化
    不过：这条测试挂了，用户在哪个具体场景会出问题
    未覆盖：这次没测什么

四样缺一，check-docs 直接报错。答不出“不过”的测试，说明它不推进任何东西，不该写。

## 需求审计（开工前必须通过）

    pnpm goal:audit

七条检查，一条不过就不许进入实现：

    A1 目标存在，且不含方案词
    A2 每个领域写清“管什么 / 不管什么”
    A3 每条 REQ 至少一条 AC
    A4 AC 验收的是用户看到的结果，不是状态码或字段
    A5 每个领域至少一条异常或边界场景
    A6 术语表至少两条，带定义
    A7 每个领域至少一条 REQ

不通过时输出缺口清单，人补 GOAL，再审计，直到通过。

## 覆盖检查（写完问，不写进文档）

```
这条 REQ 铺了哪些情形：正常 / 边界 / 异常 / 权限 / 并发
缺哪种 → 补一条 AC
某个字段或页面追不到任何 AC → 删掉
某个事件在树上找不到 AC → 补节点
```

## 完成判定

```
某条 REQ 完成 = 它下面所有 AC 有通过记录 + 一次真实演示
整体完成 = 已知必要条件满足；新需求是新增 REQ，不是推翻完成
```

## 轻量模式

默认不需要计划、不需要审查记录、不需要红灯回执。

- 小改动：读 `GOAL.md` → 改代码与测试 → 跑 `pnpm test` 与 `pnpm check:docs`。
- 涉及数据、权限、金额、删除：先写一句决策（选了什么、为什么），放在 `docs/others/adr/` 或 Feature 里。
- 跨多天、多人协作时，才建 Plan；Plan 是一次性的施工单，交付后归档。

## 什么时候不要用这套

```
纯展示页、一次性脚本、没有真实规则的 CRUD：直接写，不建树
```
