# 跨文档与跨 Plan 协作

本页只负责专业产出之间的衔接，以及跨 Plan 依赖、共享写入和组合版本的协调。各专业怎样编写、维护和验收由所属规则定义；本页不重定义产品决定、任务状态或完成门禁。

普通任务从相关 Feature、Design 和现有 Plan 开始，直接使用 [需求规则](../features/README.md)、[Plan 规则](../plans/README.md)、[测试标准](./testing.md) 与 [Release 规则](../plans/releases/README.md)。单 Plan 的重点选择与纠偏在 Plan 内完成。存在跨 Plan 依赖、共享写入、交接冲突或组合版本集成时才需要本页。

## 跨文档衔接

具体 Plan 是本轮交付的协调载体，Release 是组合交付的协调载体。按原有关系传递产出：

| 移交                                  | 提供的依据                   | 接收方核对                           |
| ------------------------------------- | ---------------------------- | ------------------------------------ |
| Feature → Plan                        | 用户目标、REQ、AC 与决定边界 | 原始目标没有遗漏，本轮范围有明确归属 |
| Plan → Contract/Test → Implementation | 目标映射、相关事实和验收设计 | 行为断言来自承诺；实现遵循专业边界   |
| Implementation → Verify               | 当前实现、迁移与同一版本     | 对应层级的真实结果和有效证据         |
| Verify → Design / Release             | 已证明结果、版本及真实缺口   | 当前事实一致，组合覆盖没有遗漏       |

表格只说明交接关系；需求尺度见需求规则，TDD 与证据见测试标准，状态和完成条件见 Plan/Release。每类产出在自己的原位置更新，不复制成一套协调台账。

## 跨 Plan 依赖与交接

- 上游负责提交明确接口及相关文件快照；下游在 dependency_contracts 引用 commit 和 paths。开发阶段可依此推进，接口变化后重新对齐，最终集成仍满足 depends_on。
- 共享 Schema、API 注册、导航等文件在 shared_files 使用同一负责人及模式。非负责人只提交业务切片和 handoff；集成人接管相关 Plan owner 后修改共享文件并集成。
- handoff 包含接口、迁移、测试入口和未完成项。接收者核对实际快照及现有证据，不能把上游局部通过当成组合完成。
- 并行工作优先不同工作区，各提交用 Ignite-Plan trailer 标明归属；依赖与写入冲突在原 Plan 对齐，不额外创建“收口”Plan 或状态表。
- 组合负责人确认纳入 Plan 的依赖、接口与迁移一致；最终验收按 Release 规则完成，同一版本的事实回写按 Design 规则执行。

例如两个 Plan 都涉及 Prisma Schema，由已声明的集成人统一修改；其他人交接业务需求与迁移信息。上游 API 改动时先更新原契约并通知实际依赖的执行者对齐；消息发送权限仍按用户授权，文档交接不自动授权对外通知。

## 发现冲突时

先指出冲突属于原始目标、规格、接口、实现还是证据，交由相应原文档的维护者修正。新事实影响重点时由当前 Plan 更新判断；冲突影响产品结果或授权边界时由人决定，独立可推进的相关任务继续。

需求变化回到 Feature，计划变化回到 Plan，实际实现变化回到 Design 和对应测试，组合范围变化回到 Release。真正需要长期解释的架构取舍才记 ADR。不得让协调文件覆盖专业真源或把未满足条件包装成完成。
